# 宿舍报修与维修工单系统 HTML 原型设计规格

## 1. 目标

根据 `doc/requirements/宿舍报修与维修工单系统需求总结 V1.md` 制作一套可直接在浏览器打开的多页面 HTML 原型，覆盖学生、维修人员和管理员三类角色。

原型用于验证信息架构、操作入口和端到端用户路径，不连接后端、不虚构接口。关键操作通过浏览器本地状态模拟，使登录、报修、接单、维修、确认、返工和异常处理能够连续演示。

## 2. 实现边界

- 采用多页面 HTML，每个主要业务场景对应独立页面。
- 共享 CSS、JavaScript、图标和演示数据。
- 使用 `localStorage` 保存当前账号及演示工单状态。
- 图片选择仅生成本地预览，不上传文件。
- 不请求网络资源，不依赖构建工具和服务端。
- 不实现需求明确排除的库存、费用、GIS、AI 派单、复杂排班和实时通信能力。
- “超时、疑似重复、派单失败、转派失败、异常工单”均作为标记展示，不作为工单业务状态。

## 3. 页面清单

### 3.1 公共入口

1. `login.html`：账号登录、演示账号说明、账号校验和按角色跳转。

### 3.2 学生端

2. `student-home.html`：学生首页、当前进度、快捷报修和最近工单。
3. `student-repair-create.html`：填写结构化位置、故障类型、描述、图片和联系方式。
4. `student-orders.html`：本人工单列表和状态筛选。
5. `student-order-detail.html`：工单信息、派单情况、维修时间线和维修结果。
6. `student-order-review.html`：确认完成、申请返工、评分和评价。

疑似重复报修以提交页弹窗呈现，允许查看已有工单或继续提交。

### 3.3 维修人员端

7. `worker-home.html`：今日工作台、待接单、超时提醒和当前任务。
8. `worker-orders.html`：本人工单列表、状态和时限筛选。
9. `worker-order-detail.html`：接单、预计完成时间和维修上下文。
10. `worker-process.html`：追加维修过程说明和现场图片。
11. `worker-materials.html`：登记和查看材料使用记录。
12. `worker-complete.html`：提交维修说明和完成图片。
13. `worker-leave.html`：请假记录、申请和审批状态。

维修中断、恢复和转派申请放在工单详情操作抽屉中。

### 3.4 管理端

14. `admin-dashboard.html`：运营概览、待办、超时和异常分布。
15. `admin-orders.html`：全部工单、组合筛选、超时和异常标记。
16. `admin-order-detail.html`：工单详情、材料、负责人和流转审计。
17. `admin-dispatch.html`：待人工派单及维修人员候选信息。
18. `admin-exceptions.html`：转派失败、多次返工、超时和其他异常。
19. `admin-transfer-approvals.html`：转派申请审批。
20. `admin-leave-approvals.html`：请假审批和受影响工单预览。
21. `admin-workers.html`：维修人员、技能、负责区域和当前负载。
22. `admin-settings.html`：故障类型、位置层级和工作时间方案。

通知入口放在各端顶栏；系统操作日志与工单流转记录在管理端工单详情内分区展示。

## 4. 登录与角色入口

固定演示账号如下：

| 角色 | 账号 | 密码 | 登录后入口 |
| --- | --- | --- | --- |
| 学生 | `student` | `123456` | 学生首页 |
| 维修人员 | `worker` | `123456` | 维修工作台 |
| 管理员 | `admin` | `123456` | 管理驾驶舱 |

登录页标注这些账号仅供原型演示。登录成功后记录当前角色；各角色页面检测登录状态和角色，不匹配时返回登录页。各端均提供退出登录和重置演示数据入口。

## 5. 核心用户路径

### 5.1 正常维修

学生登录并提交报修 → 系统模拟自动派单 → 维修人员登录并接单 → 添加过程和材料 → 提交维修结果 → 学生确认 → 提交评价 → 工单完成。

### 5.2 接单超时

学生报修 → 工单派给维修人员 A → 页面展示接单超时 → 系统模拟改派维修人员 B → B 接单并完成。

### 5.3 主动转派

维修人员接单 → 在详情中填写原因并申请转派 → 管理员审批通过 → 系统模拟匹配新维修人员 → 工单回到待接单并重新显示截止时间。

### 5.4 维修人员请假

维修人员提交请假 → 管理员查看受影响工单并审批 → 到达演示生效节点 → 工单分别显示改派成功或进入人工处理 → 原维修人员显示请假中。

### 5.5 多次返工

维修人员提交完成 → 学生申请返工 → 重复维修和验收 → 第二次返工显示管理员预警 → 第三次返工添加异常标记 → 管理员从异常工单页介入。

## 6. 视觉系统

视觉结构参考 B 站页面的信息密度、顶部导航、分区标签和内容流，但不使用其 Logo、专有图标或品牌素材。主题采用维修系统适用的红色系。

### 6.1 色彩

- 工单红：`#E53935`，用于主要操作和当前进度。
- 强调红：`#B71C1C`，用于按下状态和严重异常。
- 提示底色：`#FFF1F0`，用于错误、风险和重复提示背景。
- 页面背景：`#F6F7F9`。
- 主文字：`#18191C`。
- 次级文字：`#61666D`。
- 分隔线：`#E3E5E7`。
- 成功状态：`#2EAD65`。
- 警告状态：`#F59E0B`。

大面积区域保持中性明亮，红色仅承担动作、轨迹和提醒功能。

### 6.2 字体

使用 `"Microsoft YaHei", "PingFang SC", sans-serif`。正文行长保持易读，标题使用明确的字重和尺寸层级，不依赖网络字体。

### 6.3 布局

学生端和维修端采用移动优先结构：顶部账号栏、当前关键任务、筛选或业务内容流、底部角色导航。桌面宽度下居中显示并扩展内容宽度。

管理端采用顶部栏、左侧导航和主内容区布局。列表页以筛选条和数据表为主，详情页以概要、业务内容和审计时间线组织。

### 6.4 视觉记忆点

使用“红色工单轨迹线”贯穿列表状态、详情步骤和审计时间线，表现工单从报修到闭环的连续流转。其余装饰保持克制，避免无意义的渐变、悬浮卡片和动画堆叠。

## 7. 交互原则

- 每页只突出一个首要动作。
- 工单编号、当前状态、负责人和截止时间固定在详情的高可见区域。
- 状态名称和操作名称在所有角色页面中保持一致。
- 简短操作使用弹窗或抽屉，不单独拆页。
- 危险或不可逆操作需要二次确认。
- 操作成功后显示明确反馈，并更新后续页面可见的数据。
- 表单错误紧邻字段展示，说明具体修正方法。
- 空状态给出下一步动作。
- 键盘焦点清晰；尊重 `prefers-reduced-motion`。

## 8. 演示数据与状态

共享脚本提供初始账号、工单、维修人员、请假、转派和提醒数据。状态更新最少覆盖：

- 新建工单加入学生列表和管理端全部工单。
- 接单后由“待接单”变为“维修中”。
- 中断后变为“已中断”，恢复后回到“维修中”。
- 维修记录与材料记录加入对应工单。
- 提交维修结果后变为“待确认”。
- 学生确认后变为“已完成”，随后可评价一次。
- 学生返工后累加返工次数并进入“返工中”。
- 转派审批通过后更新负责人并回到“待接单”。
- 人工派单后更新负责人和接单截止时间。
- 重置演示数据恢复所有预置状态。

## 9. 异常与边界表现

原型必须可展示并解释以下情况：

- 登录账号或密码错误。
- 必填项缺失或联系方式格式不正确。
- 24 小时内同位置、同故障类型的疑似重复报修。
- 接单或完成期限即将到期和已经超时。
- 自动派单失败后进入管理员待办。
- 转派审批通过但重新匹配失败。
- 请假审批影响未完成工单。
- 第三次返工触发异常工单标记。
- 已完成工单不能再次执行维修动作。

## 10. 文件组织

```text
prototype/
├─ index.html
├─ login.html
├─ student-*.html
├─ worker-*.html
├─ admin-*.html
└─ assets/
   ├─ styles.css
   ├─ app.js
   ├─ data.js
   └─ icons.svg
```

`index.html` 跳转到登录页。页面不引入外部 CDN，保证双击打开即可使用。

## 11. 验证标准

- 22 个主要页面均可从对应导航或业务动作抵达，不存在断链。
- 三个演示账号可登录，并只能进入对应角色页面。
- 五条核心验收路径均可完整点击演示。
- 刷新页面后当前登录状态和已执行的演示操作仍然保留。
- 重置演示数据后恢复预置状态。
- 在约 390px 手机宽度和 1440px 桌面宽度下无横向溢出、遮挡或无法操作的控件。
- 所有表单具有标签、必填提示和失败反馈。
- 键盘可访问主要导航、按钮、表单和弹窗。
- 页面不发起外部网络请求。

## 12. 完成定义

当页面清单、角色登录、共享演示状态、五条端到端路径、响应式布局和基本可访问性全部通过验证时，本次 HTML 原型任务完成。

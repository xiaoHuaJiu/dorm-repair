# PLAN-5 自动派单设计

## 目标

在不回滚已创建工单的前提下，事务提交后异步执行自动派单；按故障类型、负责区域、人员状态、请假状态和未完成工作量筛选维修人员，通过数据库 CAS 保证同一工单仅成功派单一次，并对失败进行持久化告警和定时补偿。

## 核心设计

- `RepairDispatchService.dispatch(orderId, excludeWorkerIds, sourceType)` 是唯一派单入口。
- 初次报修在创建事务提交后向独立有界线程池提交任务；线程池拒绝或任务异常时记录派单告警。
- 定时任务扫描超时仍处于待派单且未分配人员的工单，再次调用统一派单入口。
- 候选人按技能、区域、启用状态、工作状态、有效请假依次过滤，批量统计未完成工单数，按工作量升序、维修人员 ID 升序选人。
- 工单更新使用带来源状态和原负责人条件的 CAS；CAS 成功后写入工单流转记录，两者处于同一事务并使用同一个派单时间。
- 接单截止时间按有效工作时间累计 30 分钟。`repair_holiday_calendar` 的法定节假日/调休上班日配置优先于周末规则，最多向后搜索 366 天；找不到有效工作时间时派单失败。
- 派单失败时工单保持待派单、清空负责人，并以工单、来源和失败原因为维度去重写入 `repair_dispatch_alert`。

## 异步可靠性边界

线程池不作为可靠存储。工单表中的待派单状态是可恢复事实，定时补偿负责发现未执行、拒绝执行或进程中断的任务。数据库仍是最终事实来源，不引入消息队列和 Redis 派单锁。

## 数据结构

- `repair_holiday_calendar`：日期唯一，`day_type=1` 表示放假，`day_type=2` 表示调休上班；导入附件中的 2026 年 39 条配置。
- `repair_dispatch_alert`：记录工单、派单来源、失败原因、状态、失败详情、首次/最近发生时间和发生次数；未处理记录使用唯一键去重。

## 接口影响

不新增 HTTP 接口。学生创建工单接口仍返回工单持久化结果；响应返回时异步派单可能尚未完成，前端不得把创建成功等同于派单成功。

## 验证

覆盖候选筛选、工作量排序、区域层级、请假过滤、有效工作时间矩阵、CAS 并发、事务回滚、异步提交后执行、线程池拒绝、补偿扫描、失败告警去重、SQL 索引执行计划和真实 MySQL 集成测试。

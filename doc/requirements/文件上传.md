# 宿舍报修与维修工单系统——文件上传功能详细设计方案

> 适用范围：报修图片/视频、维修过程图片/视频、返工图片/视频  
> 技术方案：Spring Boot + MyBatis + MinIO + Vue3 + Element Plus  
> 上传方式：前端上传到 Spring Boot，Spring Boot 再统一上传至 MinIO  
> 设计目标：建立可复用的公共 `FileService`，业务模块只保存文件引用，不直接处理 MinIO 细节。

---

# 一、建设目标

当前系统仅支持保存已有图片或视频地址，尚未形成真正的文件上传能力。

本阶段补齐完整链路：

```text
前端选择图片/视频
        ↓
公共上传接口
        ↓
Spring Boot
        ↓
文件合法性校验
        ↓
MinIO
        ↓
文件元数据落库
        ↓
返回 fileId + previewUrl
        ↓
业务接口提交 fileId
        ↓
建立业务记录与文件关联
```

本次覆盖三个业务场景：

```text
1. 学生报修
   └─ 报修图片 / 视频

2. 维修人员处理工单
   └─ 维修过程图片 / 视频

3. 学生发起返工
   └─ 返工图片 / 视频
```

本阶段不做：

```text
分片上传
断点续传
秒传
文件 MD5 去重
前端直传 MinIO
转码
视频压缩
图片 OCR
内容审核
消息队列异步上传
```

后续如出现大视频、大并发上传场景，可以将上传链路升级为 MinIO Presigned URL，但本阶段业务表和文件引用模型无需推翻。

# 二、核心设计原则

## 2.1 文件存储与业务解耦

业务模块不直接调用 MinIO：

```text
RepairService
RepairProcessService
ReworkService
```

统一依赖：

```text
FileService
```

`FileService` 内部再调用 MinIO。

关系：

```text
业务 Service
     ↓
FileService
     ↓
MinioClient
```

这样未来切换对象存储实现时，业务层无需修改。

---

## 2.2 数据库保存 fileId，不保存固定 MinIO URL

不推荐业务表直接保存：

```text
http://192.168.1.20:9000/repair-files/repair/2026/09/24/xxx.jpg
```

推荐保存：

```text
file_id = 10001
```

真正的 MinIO 信息统一放在公共文件表。

原因：

1. MinIO 域名可能变化。
2. Bucket 可能调整。
3. 私有 Bucket 的访问地址可能是临时签名 URL。
4. 删除、权限控制、垃圾文件清理都需要文件元数据。
5. 同一套文件能力可复用于其他模块。

---

## 2.3 MinIO Bucket 尽量统一

建议：

```text
Bucket：repair-files
```

不为每种业务创建单独 Bucket。

对象路径按业务类型区分：

```text
repair-files
├── repair/
│   └── 2026/09/24/xxx.jpg
├── process/
│   └── 2026/09/24/xxx.mp4
└── rework/
    └── 2026/09/24/xxx.jpg
```

# 十、为什么拆三个附件关联表

也可以设计一个：

```text
biz_file_relation

biz_type
biz_id
file_id
```

统一关联所有业务。

但当前项目业务范围明确：

```text
报修
维修过程
返工
```

拆成三个关系表有几个好处：

1. 表意更加清晰。
2. SQL 查询简单。
3. 不需要大量 `biz_type + biz_id` 判断。
4. 不会出现不同业务 ID 相同导致理解混乱。
5. 后续查询工单完整详情更加直接。

当前项目不需要为了所谓“通用性”引入过度抽象。

因此：

> 公共文件存储统一，业务关联关系分开。

这是当前更合适的方案。

# 二十一、objectName 生成

```java
private String buildObjectName(
        FileBizTypeEnum bizType,
        String suffix) {

    LocalDate now = LocalDate.now();

    return String.format(
            "%s/%d/%02d/%02d/%s.%s",
            bizType.getPath(),
            now.getYear(),
            now.getMonthValue(),
            now.getDayOfMonth(),
            UUID.randomUUID().toString().replace("-", ""),
            suffix
    );
}
```

```java
public enum FileBizTypeEnum {

    REPAIR("repair"),

    PROCESS("process"),

    REWORK("rework");

    private final String path;

}
```

# 二十七、文件校验逻辑

基础校验建议：

```text
1. file != null
2. !file.isEmpty()
3. file.size > 0
4. 后缀允许
5. contentType 允许
6. 文件大小允许
```

不要只校验文件后缀。

例如：

```text
xxx.exe
```

人为改名：

```text
xxx.jpg
```

仅校验 `.jpg` 不安全。

本阶段至少做到：

```text
后缀 + MIME
```

如果项目已有 Apache Tika，可以进一步识别真实文件类型。

没有的话，不需要为了本阶段单独引入复杂依赖。

# 二十八、核心上传伪代码

```java
@Transactional(rollbackFor = Exception.class)
@Override
public FileUploadVO upload(
        MultipartFile file,
        String bizTypeCode) {

    // 1. 基础检查
    if (file == null || file.isEmpty()) {
        throw new BusinessException("上传文件不能为空");
    }

    // 2. bizType
    FileBizTypeEnum bizType =
            FileBizTypeEnum.fromCode(bizTypeCode);

    // 3. 获取后缀
    String originalName = file.getOriginalFilename();
    String suffix = getSuffix(originalName);

    // 4. 判断文件类型并校验
    FileTypeEnum fileType =
            validateFile(file, suffix);

    // 5. objectName
    String objectName =
            buildObjectName(bizType, suffix);

    try {

        // 6. MinIO上传
        minioClient.putObject(
                PutObjectArgs.builder()
                        .bucket(bucketName)
                        .object(objectName)
                        .stream(
                                file.getInputStream(),
                                file.getSize(),
                                -1
                        )
                        .contentType(file.getContentType())
                        .build()
        );

        // 7. 文件记录
        SysFile sysFile = new SysFile();

        sysFile.setOriginalName(originalName);
        sysFile.setBucketName(bucketName);
        sysFile.setObjectName(objectName);
        sysFile.setFileType(fileType.name());
        sysFile.setContentType(file.getContentType());
        sysFile.setFileSuffix(suffix);
        sysFile.setFileSize(file.getSize());
        sysFile.setBizType(bizType.name());
        sysFile.setStatus(1);
        sysFile.setCreateBy(getCurrentUserId());

        sysFileMapper.insert(sysFile);

        // 8. 返回结果
        return buildUploadVO(sysFile);

    } catch (Exception e) {

        // MinIO已上传但数据库失败时进行补偿删除
        removeObjectQuietly(objectName);

        throw new BusinessException(
                "文件上传失败"
        );
    }
}
```

# 二十九、一个重要问题：MinIO 与数据库不是同一个事务

Spring：

```java
@Transactional
```

只能回滚数据库。

不能自动回滚 MinIO。

可能出现：

```text
MinIO 上传成功
↓
数据库插入失败
↓
事务回滚
↓
MinIO 仍然存在文件
```

因此上传方法必须做补偿。

推荐：

```text
MinIO成功
↓
DB失败
↓
catch
↓
主动 removeObject
```

这样足够解决当前需求。

暂时不需要引入：

```text
分布式事务
Seata
可靠消息
```

---

# 三十、反向异常情况

另一种情况：

```text
数据库成功
MinIO失败
```

不会发生，因为设计顺序应该是：

```text
先上传 MinIO
再插数据库
```

MinIO 上传失败则直接：

```text
不写数据库
```

# 三十一、业务文件绑定规则

上传成功并不代表文件已经属于某个业务。

例如学生上传：

```text

fileId = 10002
```

然后可能关闭页面，没有提交报修单。

所以区分两个概念：

```text
文件已上传
≠
文件已绑定业务
```

业务提交时才建立关系。

# 四十六、垃圾文件清理策略

建议：

```text
每天凌晨执行一次
```

查找：

```text
create_time < NOW() - 24小时
AND deleted = 0
AND status = 1
AND 不存在任何业务关联
```

然后：

```text
删除 MinIO 对象
↓

```

# 四十七、为什么设置 24 小时

```text

↓
```

# 四十八、孤儿文件判断 SQL 思路

```sql
SELECT f.id
FROM sys_file f
WHERE f.deleted = 0
  AND f.status = 1
  AND f.create_time < DATE_SUB(NOW(), INTERVAL 1 DAY)
  AND NOT EXISTS (
      SELECT 1
      FROM repair_order_file rof
      WHERE rof.file_id = f.id
  )
  AND NOT EXISTS (
      SELECT 1
      FROM repair_process_file rpf
      WHERE rpf.file_id = f.id
  )
  AND NOT EXISTS (
      SELECT 1
      FROM repair_rework_file rwf
      WHERE rwf.file_id = f.id
  );
```

# 五十五、绑定文件校验伪代码

```java
private List<SysFile> validateFiles(
        List<Long> fileIds,
        FileBizTypeEnum bizType,
        Long currentUserId) {

    if (CollectionUtils.isEmpty(fileIds)) {
        return Collections.emptyList();
    }

    List<SysFile> files =
            sysFileMapper.selectByIds(fileIds);

    if (files.size() != fileIds.size()) {
        throw new BusinessException(
                "存在无效附件"
        );
    }

    for (SysFile file : files) {

        if (file.getStatus() != 1) {
            throw new BusinessException(
                    "存在未上传成功的附件"
            );
        }

        if (!bizType.name()
                .equals(file.getBizType())) {

            throw new BusinessException(
                    "附件业务类型错误"
            );
        }

        if (!currentUserId
                .equals(file.getCreateBy())) {

            throw new BusinessException(
                    "无权使用该附件"
            );
        }
    }

    return files;
}
```

# 五十六、创建报修事务

创建报修建议：

```java

public Long createRepair(
        CreateRepairDTO dto) {

    List<SysFile> files =
        fileService.validateBizFiles(
            dto.getFileIds(),
            REPAIR,
            currentUserId

    // 2. 创建工单
    RepairOrder order = ...;

    repairOrderMapper.insert(order);
```

# 五十七、上传本身不要放进“创建工单事务”

错误设计：

```text

MultipartFile[]
+
工单参数
```

然后一个接口里：

```text

创建附件关系
```

虽然能实现，但不推荐。

原因：

1. 接口职责混乱。
2. 文件上传时间可能较长。

5. 后续改直传 MinIO 很困难。

因此保持：

```text

+
业务提交接口
```

两步。

# 八十一、是否允许同一个 fileId 绑定多个业务

建议：

> 不允许。

例如：

```text
fileId=100
```

不应该同时属于：

```text
报修单 A
报修单 B
```

上传文件本质应该是一次业务附件。

绑定时最好检查：

```text
fileId 是否已经出现在任何业务关联表
```

如果已经绑定：

```text
拒绝再次绑定
```

避免跨业务复用导致删除和权限复杂化。

到 `sys_file` 中。

# 八十三、为什么不在 sys_file 保存 biz_id

如果设计：

```text
sys_file
biz_type
biz_id
```

则上传时：

```text
业务还没创建
```

根本拿不到 biz_id。

之后需要二次 UPDATE。

而且会把公共文件表和业务主键关系绑定过紧。

因此不推荐。

# 九十二、验收标准

## 上传

- JPG/JPEG/PNG/WebP 上传成功。
- MP4/MOV/WebM 上传成功。
- 非允许文件被拒绝。
- 超大文件被拒绝。
- 上传后 MinIO 对象存在。
- `sys_file` 数据正确。
- `object_name` 不使用原文件名作为存储名。

---

## 报修

- 学生可上传多个图片/视频。
- 创建报修时只提交 fileId。
- 关系表正确建立。
- 工单详情能返回图片/视频。
- 其他用户不能绑定该学生上传的文件。

---

## 维修过程

- 维修人员上传文件使用 PROCESS。
- 学生不能伪造 PROCESS 上传。
- 过程记录与附件正确绑定。
- 工单详情可查询维修过程附件。

---

## 返工

- 学生上传文件使用 REWORK。
- 返工记录与附件正确关联。
- 维修人员和管理员可按权限查看。

---

## 删除

- 未绑定文件可以删除。
- 已绑定文件不能通过公共删除接口直接删除。
- MinIO 删除成功后数据库逻辑删除。

---

## 异常

- MinIO 上传失败不产生 DB 文件记录。
- MinIO 成功但 DB 失败时执行 MinIO 补偿删除。
- 用户上传但未提交业务的文件最终能被孤儿文件任务清理。

# 九十三、最终推荐结构

```text
                            ┌──────────────┐
                            │  MinIO       │
                            └──────▲───────┘
                                   │
                             FileService
                                   │
                            ┌──────┴───────┐
                            │ sys_file     │
                            └──────▲───────┘
                                   │ fileId
             ┌─────────────────────┼─────────────────────┐
             │                     │                     │
             │                     │                     │
  repair_order_file    repair_process_file    repair_rework_file
             │                     │                     │
             ▼                     ▼                     ▼
      repair_order          repair_process          repair_rework
```

公共层只解决：

```text
文件怎么上传
文件存在哪里
文件是否合法
文件如何访问
文件如何删除
```

业务层解决：

```text
文件属于谁
属于哪个工单
谁可以查看
什么时候允许修改
```

两者职责分开。

# 九十四、最终实施结论

本项目当前采用：

```text
前端
↓
Spring Boot MultipartFile
↓
公共 FileService
↓
MinIO
↓
sys_file
```

上传成功返回：

```text
fileId
```

三类业务分别通过：

```text
repair_order_file
repair_process_file
repair_rework_file
```

建立关联。

MinIO Bucket 使用私有桶：

```text
repair-files
```

文件路径：

```text
repair/yyyy/MM/dd/UUID.ext
process/yyyy/MM/dd/UUID.ext
rework/yyyy/MM/dd/UUID.ext
```

数据库业务表只保存文件关系，不保存固定 URL。

访问时动态生成临时地址。

对于未绑定业务的上传文件：

```text
用户主动删除
+
24小时定时垃圾清理
```

双重处理。

这个设计可以直接满足当前：

```text
报修图片/视频
维修过程图片/视频
返工图片/视频
```

三类业务，同时保留以后升级 MinIO 直传、视频分片上传的扩展空间，而不会让当前实现复杂化。

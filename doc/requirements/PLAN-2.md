# 五、任务 2.1：密码安全能力

## 5.1 目标

统一解决：

```
用户密码如何存储
登录密码如何校验
注册密码如何处理
```

禁止业务代码自行处理密码。

# 六、密码存储原则

用户密码：

> 不保存明文，不保存可逆密文。

数据库字段：

```
sys_user.password
```

保存的是：

```
密码哈希结果
```

例如：

```
$2a$10$...
```

# 七、推荐密码算法

当前项目已经使用 Spring Security，因此优先使用：

```
BCryptPasswordEncoder
```

注册：

```
passwordEncoder.encode(rawPassword)
```

登录：

```
passwordEncoder.matches(
    rawPassword,
    encodedPassword
)
```

# 八、为什么密码不用普通 AES 加密

AES 属于可逆加密：

```
原密码
↓
AES
↓
密文

密文
↓
密钥
↓
原密码
```

一旦：

```
数据库
+
加密密钥
```

同时泄露，所有密码都可以恢复。

密码认证并不需要知道用户原始密码，因此应该使用：

```
单向哈希
```

# 九、PasswordEncoder 配置

建议建立统一 Bean：

```
@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
}
```

所有：

```
用户注册
密码修改
密码重置
登录校验
```

统一使用该 Bean。

不要自行：

```
new BCryptPasswordEncoder()
```

散落在不同 Service。

# 十、通用加密工具边界

如果后续系统还存在：

```
手机号脱敏
敏感字段加密
Token
签名
```

可以单独建设：

```
CryptoUtils
```

但：

```
密码
```

不要经过通用 `CryptoUtils.encrypt()`。

密码应该明确走：

```
PasswordEncoder
```

从概念上区分：

```
密码哈希
≠
业务数据加密
```

# 十一、密码安全验收

至少验证：

```
相同明文密码注册两个账号
↓
数据库 password 字符串可以不同

原密码不可直接从数据库读取

正确密码 matches = true

错误密码 matches = false
```

同时检查日志：

```
禁止打印 rawPassword
禁止打印完整密码 hash
```



# 十二、任务 2.2：用户注册

## 12.1 目标

建立：

```
sys_user
```

的正式用户创建能力。

# 十三、注册角色范围

系统包含：

```
学生
维修人员
管理员
```

但区分自主注册与管理员创建账号。

### 学生

允许普通注册：

```
role_type = STUDENT
```

### 维修人员

不允许前端匿名用户自行注册成维修人员。

由管理员创建 / 绑定

### 管理员

不允许公开注册。

管理员账号：

```
初始化 或 由已有管理员创建
```

# 十四、公开注册安全原则

公开注册接口不能接受：

```
{
  "roleType": 3
}
```

然后直接创建管理员。

公开注册接口服务端固定：

```
role_type = STUDENT
```

角色由服务端决定。

# 十五、注册请求

建议：

```
RegisterDTO
```

至少：

```
username
password
confirmPassword
realName
phone
```

不接受：

```
userId
roleType
status
createTime
```

等服务端字段。

# 十六、注册校验

至少校验：

```
用户名不能为空

用户名长度合法

用户名唯一

密码不能为空

密码满足长度要求

password = confirmPassword

姓名合法

手机号格式合法

手机号是否要求唯一按最终业务规则执行
```

# 十七、注册流程

```
接收 RegisterDTO
        ↓
Bean Validation
        ↓
检查用户名唯一
        ↓
检查两次密码一致
        ↓
BCrypt hash
        ↓
创建 sys_user
        ↓
role_type = STUDENT
        ↓
status = 正常
        ↓
返回注册成功
```

# 十八、并发注册保护

`username` 数据库已经有：

```
UNIQUE
```

因此：

```
Service 先查 + 数据库唯一索引最终兜底
```

即可。

不需要为注册用户名引入 Redis 分布式锁。

出现并发：

```
两个请求同时注册同一 username
```

最终只能一个 INSERT 成功。

另一个转换成明确业务错误：

```
USER-A-xxxxx

HTTP 409

userTip:
该用户名已被使用，请更换后重试。
```

# 十九、注册响应

注册成功：

```
HTTP 200
```

原则上：

> 不返回 password 字段。

甚至不要返回：

```
password hash
```

# 二十、用户注册验收

```
正常学生注册
→ 成功

重复 username
→ 409

密码不一致
→ 400

密码格式错误
→ 400

匿名提交 roleType=ADMIN
→ 无法创建管理员

数据库 password
→ 非明文

正确密码
→ 可以登录
```

```

→ 楼栋

→ 房间

```

```
parent 类型是否合法

```

是否允许同名根据业务确定，但至少：

```
同一个父节点
+
同一节点类型
+
同名
```

拦截。

# 三十八、位置修改

允许：

```
名称
排序
备注
```

第一期建议：

> 不支持随意修改 parentId。

因为位置节点已经被负责区域、工单引用后，更换父节点会改变业务含义。

如果需要调整层级，可以后续单独设计迁移功能。

# 三十九、位置启停

采用：

```
status
```

而不是删除。

停用父节点时需要明确：

> 子节点不一定修改数据库状态，但前端业务选择时整个子树都视为不可选。

避免批量更新所有子节点。

也可以在查询时计算有效性。

# 七十四、生效日期冲突

启用状态的工作时间方案：

> 生效日期区间不能互相重叠。

例如已有：

```
05-01 ~ 09-30
```

再创建：

```

```

```
不允许
```

```

```

将产生歧义。

# 七十五、区间冲突判断

两个区间：

```
oldStart
oldEnd

newStart
newEnd
```

存在交集条件：

```
oldStart <= newEnd
AND
oldEnd >= newStart
```

新增和修改都要检查。

修改时排除当前记录。

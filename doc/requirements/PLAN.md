根据这四份附件，我建议不要按“数据库表 → 一个表一个 CRUD”的顺序推进，而是按照**业务依赖链 + 状态流转依赖**来排开发计划。

系统主链路已经非常明确：学生报修 → 重复检测 → 自动派单 → 维修人员接单 → 维修处理/中断/恢复 → 提交结果 → 学生确认 → 评价或返工；管理员承担派单失败、转派失败、多次返工、超时等异常兜底。

我下面按**1 后端 + 1 前端并行开发**估算，单位用“人日”。如果目前主要是你一个人全栈开发，可以把总人日基本看作实际开发天数；如果前后端各 1 人，则部分阶段可以重叠。

# 一、开发前先锁定两个基础问题

## 1. 位置模型要先最终定版

现在附件里实际上存在一个需要先处理的地方。

核心数据表设计里仍然写的是：

- `sys_user`
- 校区表
- 区域表
- 楼栋表
- 房间表

如果现有系统已有这些表则复用。

而当前 DDL 中只设计了 `repair_worker_area_scope`，字段仍然是：

```
campus_id
area_id
building_id
```

用于表示“负责整个校区 / 整个区域 / 指定楼栋”。

但你之前已经确定要增加：

> 区域树：单位 → 区域 → 楼栋

那么正式开发前建议先把这个位置基础表补入 DDL，并决定：

```
repair_area
id
parent_id
node_type
name
sort_no
status
...
```

以及工单到底：

```
A. 继续存 campus_id / area_id / building_id / room_id
```

还是：

```
B. 改成 location_node_id + room_id
```

按照现在已有 SQL、索引和派单设计，**我建议第一期保持 A**。区域树负责配置和级联选择，工单继续冗余保存各层 ID。这样不用把已经设计好的重复报修索引、区域范围索引、派单 SQL 全部推翻。

这是 **P0 阻塞项，0.5~1 人日**。

# 八、阶段 5：自动派单核心

**估时：3~4 人日**

这是整个项目最重要的 Service，建议独立：

```
RepairDispatchService
```

不要散在报修、超时、请假、转派四套代码里。

所有场景统一调用：

```
dispatch(orderId, excludeWorkerIds, sourceType)
```

## 派单算法

```
① 根据 fault_type 找技能匹配维修人员
↓
② 根据位置过滤负责范围
↓
③ 排除停用 / 请假
↓
④ 排除本次不能再次派给的人
↓
⑤ 统计候选维修人员未完成工单
↓
⑥ 最少者优先
↓
⑦ 计算接单截止时间
↓
⑧ 更新 repair_order
↓
⑨ 写 repair_order_flow
```

数据库索引与这个算法是一一对应的：

```
idx_fault_worker
idx_scope_location
idx_worker_work_status
idx_order_assignee_status
idx_schedule_effective
```

## 派单成功

```
status = 待接单
current_assignee_id = worker
dispatch_time = now
accept_deadline = 计算结果
```

## 派单失败

仍保持：

```
status = 待派单
current_assignee_id = NULL
```

并生成管理员异常提醒/待办。

需求的底线是：

> 任何自动处理失败都不能让工单无人负责且无人知晓。宿舍报修与维修工单系统需求总结 V1.mdMD

### 验收

至少覆盖：

```
只有1名匹配人员
多个候选人
技能不匹配
区域不匹配
请假人员过滤
停用人员过滤
工作量不同
工作量相同
无候选人
原维修人员需要排除
跨下班时间计算 accept_deadline
```

# 十三、阶段 10：超时、提醒与定时任务

**估时：4~5 人日**

建议放在主流程跑通之后做。

至少包括：

```
接单10分钟提醒
接单5分钟提醒
接单0分钟超时

完成10分钟提醒
完成5分钟提醒
完成0分钟超时

请假开始
请假结束
```

## 接单超时

```
status = 1
AND accept_deadline <= NOW()
```

然后：

```
解除原负责人
↓
重新调用 RepairDispatchService
↓
成功 / 待人工派单
```

## 完成超时

这里不要改工单状态。

系统定义明确：

> 超时不是业务状态。

通过：

```
NOW() > complete_deadline
```

动态判定即可。

## 防重复提醒

必须使用：

```
repair_reminder_record
```

并利用：

```
UNIQUE(
 order_id,
 reminder_type,
 reminder_level,
 deadline_time,
 receiver_id
)
```

保证一分钟扫一次也不会重复发送。

### 验收

这里建议专门使用构造数据，不等真实 30 分钟：

```
deadline = now + 10min
deadline = now + 5min
deadline = now
deadline < now
```

验证：

```
提醒只发送一次
任务重复执行不重复提醒
```

# 十七、阶段 14：联调、并发与状态机验收

**估时：4~5 人日**

不要只测正常链路。

需要重点测状态竞争：

```
维修人员重复点接单

接单同时超时任务执行

管理员审批转派时维修人员提交完成

学生重复确认

学生重复返工

评价重复提交

请假任务重复执行

超时扫描重复执行

管理员和系统同时转派
```

核心写操作建议统一采用：

```
WHERE id = ?
AND status = 预期状态
```

做状态 CAS。

例如接单：

```
UPDATE repair_order
SET status = 2,
    accept_time = NOW()
WHERE id = ?
  AND status = 1
  AND current_assignee_id = ?;
```

返回：

```
affectedRows = 1
```

才算成功。

这样比到处上分布式锁更简单，也更符合当前这个系统的规模。

# 十八、并行开发边界

真正可以并行的是下面这些。

| 工作包          | 可以并行     | 前置依赖                |
| --------------- | ------------ | ----------------------- |
| 故障类型 CRUD   | 是           | 基础工程                |
| 位置树 CRUD     | 是           | 基础工程                |
| 维修人员 CRUD   | 是           | 用户体系                |
| 工作时间 CRUD   | 是           | 基础工程                |
| 技能配置        | 是           | 维修人员 + 故障类型     |
| 区域配置        | 是           | 维修人员 + 位置         |
| 三端工单列表 UI | 是           | API 字段先定            |
| 工单详情 UI     | 是           | VO 先定                 |
| 维修过程        | 是           | 接单完成                |
| 材料记录        | 是           | 接单完成                |
| 转派申请页面    | 是           | 工单基础完成            |
| 请假 CRUD       | 是           | 维修人员完成            |
| 评价            | 是           | 待确认流程              |
| 自动派单        | **不可提前** | 技能+区域+人员+工作时间 |
| 接单超时        | **不可提前** | 自动派单                |
| 请假自动转派    | **不可提前** | 自动派单                |
| 转派审批执行    | **不可提前** | 自动派单                |
| 返工            | **不可提前** | 提交维修结果            |
| 统计查询        | **建议最后** | 状态口径稳定            |

最重要的边界就是：

> **任何涉及“重新找维修人员”的功能都不要自己写派单逻辑，全部等 `RepairDispatchService` 稳定后复用它。**

否则你最终会有：

```
学生报修派单算法
接单超时派单算法
请假转派算法
转派审批算法
管理员异常算法
```

五套几乎一样的逻辑，后面一定不一致。

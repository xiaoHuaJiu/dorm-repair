# 宿舍报修与维修工单系统需求总结 V1

## 一、系统角色

系统包含三个角色：

1. **管理员**
   - 管理故障类型、维修人员、负责区域等基础配置。
   - 查看全部报修工单。
   - 查看维修过程和材料使用情况。
   - 处理人工派单、转派失败、多次返工等异常工单。
   - 接收异常及超时提醒。
   - 查看完整工单流转及审计记录。
2. **维修人员**
   - 接收系统派发的维修工单。
   - 接单并填写预计完成时间。
   - 记录维修过程。
   - 登记使用材料。
   - 中断、恢复维修。
   - 发起转派申请。
   - 提交维修结果。
3. **学生**
   - 提交报修。
   - 查看报修进度和维修过程。
   - 查看维修结果。
   - 确认维修完成。
   - 评价维修服务。
   - 维修未解决时申请返工。

# 二、总体业务流程

```
学生提交报修信息
        ↓
系统根据故障类型和负责范围自动派单
        ↓
维修人员在规定时间内接单
        ↓
维修人员处理故障
        ↓
提交维修结果
        ↓
学生确认
   ↙           ↘
完成评价       申请返工
```

系统需要对整个过程进行状态跟踪、负责人跟踪、时间跟踪和审计记录。

# 三、报修单基础信息

学生提交报修时填写：

```
故障位置
故障类型
问题描述
现场图片（可选）
报修人
联系方式
报修时间
```

其中故障位置采用结构化方式记录：

```
校区
→ 区域
→ 楼栋
→ 房间
→ 具体位置描述
```

例如：

```
东校区
→ 学生生活区
→ 3号楼
→ 502室
→ 卫生间洗手池下方
```

结构化位置主要用于：

- 自动派单；
- 维修人员负责范围匹配；
- 重复报修识别；
- 后续故障统计分析。

# 四、自动派单流程

自动派单逻辑：

```
故障类型
        ↓
找到能够维修该故障类型的维修人员
        ↓
根据故障位置过滤负责区域
        ↓
过滤停用 / 休假 / 不可接单人员
        ↓
按照当前未完成工单数量排序
        ↓
优先选择未完成工单最少的维修人员
        ↓
派单
```

第一阶段不引入复杂的权重评分算法，以：

> **故障类型 + 负责区域 + 当前工作量**

作为主要派单依据。

# 五、派单失败处理

如果没有找到符合条件的维修人员：

```
自动派单
   ↓
匹配失败
   ↓
进入待派单列表
   ↓
通知管理员
   ↓
管理员人工派单
```

核心原则：

> **任何派单失败都不能导致工单在无人负责、无人知晓的情况下停留。**

所有无法自动处理的异常最终都由管理员兜底。

# 六、响应超时机制

维修人员收到派单后：

> **原则上必须在30分钟内接单。**

**30**分钟接单时限按“有效工作时间”累计

有工作时间表，接单截止时间不能简单：

```
dispatch_time + 30min
```

而要定义成：

> 从派单时刻开始累计30分钟“维修人员有效工作时间”。

例如夏季：

```
工作时间：08:00 - 18:00
```

17:50派单：

```
17:50 - 18:00
消耗10分钟
```

还剩：

```
20分钟
```

第二天08:00继续累计：

```
08:20
```

所以：

```
接单截止时间 = 第二天08:20
```

如果派单发生在：

```
20:00
```

则不应该从20:00开始计时，而应该：

```
第二天08:00开始
↓
08:30截止
```

因此最好在派单成功时就计算并保存：

```
accept_deadline
```

后续提醒任务直接根据这个时间判断即可，不需要每次重新算。

因此：

> 响应时限计算需要排除维修人员的非工作时间。

后续需要结合：

- 工作时间；
- 排班；
- 休息日；
- 请假状态；

计算实际接单截止时间。

如果到截止时间仍未接单：

```
接单超时
    ↓
当前维修人员解除派单
    ↓
重新执行自动派单
    ↓
其他符合条件维修人员
```

如果重新派单仍失败：

```
进入待人工派单
↓
通知管理员
```

# 七、响应提醒

维修人员接单截止时间前：

```
剩余10分钟 → 提醒
剩余5分钟  → 提醒
剩余0分钟  → 超时提醒 + 自动转派
```

管理员根据需要也可以收到对应异常提醒。

# 八、维修完成时限

维修人员接单时可以选择：

> **预计完成时间**

此时：

```
维修截止时间 = 预计完成时间
```

如果维修人员没有填写预计完成时间：

```
维修截止时间 = 接单时间 + 24小时
```

后续如果涉及非工作时间是否计入24小时，可以再根据业务要求确定。

# 九、维修完成提醒

距离维修截止时间：

```
剩余10分钟 → 提醒
剩余5分钟  → 提醒
剩余0分钟  → 超时提醒
```

维修超时以后：

- 工单仍保持当前业务状态；
- 标记为超时；
- 通知维修人员；
- 通知管理员。

因此：

> **“超时”不作为独立工单状态。**

通过：

```
当前时间 > 维修截止时间
```

动态判断即可。

# 十、维修过程记录

维修人员在维修过程中可以持续添加处理记录。

每条处理记录至少记录：

```
工单ID
维修人员
处理内容
现场图片（可选）
记录时间
```

例如：

```
09:05 到达现场，检查发现水龙头阀芯损坏。

09:20 仓库暂无对应阀芯，申请暂停维修。

14:10 获取材料后继续维修。

14:25 完成阀芯更换并测试。
```

维修过程：

- 维修人员可以查看；
- 管理员可以查看；
- 学生可以查看。

如果以后存在内部备注，可单独增加“管理员/维修人员可见”的内部记录类型。

# 十一、维修材料记录

维修人员记录本次维修实际使用的材料，例如：

```
材料名称
规格
数量
使用时间
记录人员
```

建议权限：

```
维修人员：可记录、查看本人相关工单材料
管理员：可查看全部材料记录
学生：默认不展示内部材料明细
```

学生只需要看到：

```
维修结果
处理说明
完成图片
```

如果以后系统涉及费用结算，再考虑向学生展示材料和费用。

# 十二、维修中断

维修过程中如果暂时无法继续，可以进行中断。

中断原因：

```
等待材料
需要第三方介入
现场条件不允许
其他
```

记录：

```
中断时间
中断原因
恢复时间
```

流程：

```
维修中
 ↓
维修中断
 ↓
等待条件恢复
 ↓
恢复维修
 ↓
维修中
```

工单进入：

```
已中断
```

状态。

恢复后重新进入：

```
维修中
```

状态。

# 十三、重复报修识别

学生提交报修时，系统检查：

```
同一校区
+
同一区域
+
同一楼栋
+
同一房间
+
同一故障类型
+
24小时以内
+
存在未关闭工单
```

未关闭工单主要包括：

```
待派单
待接单
维修中
已中断
返工中
```

满足条件时：

```
系统发现疑似重复报修
        ↓
提示学生：

“当前位置存在相似未完成工单
WO202609160023，是否仍要提交？”
```

学生可以：

```
查看已有工单
```

或者：

```
仍然提交
```

系统只负责：

> **识别和提示疑似重复报修。**

不自动禁止学生提交。

# 十四、重复报修与返工的区别

## 重复报修

含义：

> 原工单尚未完成时，学生又提交了一个相似故障。

例如：

```
10:00 学生A报告502宿舍洗手池漏水

10:20 学生B再次报告502宿舍洗手池漏水
```

此时属于：

```
两张独立工单
+
疑似重复关系
```

## 返工

含义：

> 原工单已经由维修人员提交完成，但学生确认时认为问题没有解决。

流程：

```
维修人员提交完成
↓
学生验收
↓
发现仍未解决
↓
申请返工
```

返工属于：

> **原工单重新进入维修流程。**

不会重新创建一张完全独立的新报修工单。

# 十五、返工流程

```
维修人员提交完成
        ↓
待学生确认
    ↙          ↘
确认完成       申请返工
   ↓              ↓
待评价          返工中
   ↓              ↓
评价完成       再次维修
   ↓
已完成
```

每次返工：

```
rework_count + 1
```

同时记录：

```
返工申请人
返工原因
返工时间
返工次数
```

# 十六、多次返工与异常工单

### 第一次返工

```
返工次数 = 1
↓
原维修人员继续处理
```

### 第二次返工

```
返工次数 = 2
↓
通知管理员
↓
管理员收到异常预警
```

管理员可以继续让原维修人员处理，也可以人工干预。

### 第三次及以上返工

```
返工次数 >= 3
↓
标记异常工单
↓
必须管理员介入
```

管理员可以：

```
更换维修人员
更换维修方案
转第三方维修
直接更换设备
其他人工处理措施
```

“异常工单”建议作为：

```
异常标记 / exception_flag
```

而不是再增加一个独立业务状态。

这样工单仍然可以处于：

```
返工中
维修中
已中断
```

等真实状态。

# 十七、维修人员转派

维修人员认为自己无法继续处理时，可以：

> **发起转派申请。**

转派原因：

```
不属于本人负责范围
不具备对应技能
当前无法处理
需要其他工种
工作量过大
其他
```

转派过程中记录：

```
原负责人
新负责人
转派发起人
转派原因
转派时间
```

# 十八、转派处理流程

```
维修人员发起转派申请
        ↓
填写转派原因
        ↓
管理员审批
   ↙            ↘
驳回            同意
 ↓               ↓
原维修人员      系统重新匹配
继续处理          ↓
             自动选择合适维修人员
              ↙          ↘
            成功          失败
             ↓             ↓
          转派成功      通知管理员
                           ↓
                     管理员人工处理
```

如果匹配失败：

```
第一次重新匹配失败
↓
尝试其他符合条件维修人员
↓
仍然失败
↓
进入待派单列表
↓
通知管理员
↓
管理员人工派单
```

仍然遵循系统核心底线：

> **任何自动处理失败都必须形成明确的管理员待办或异常提醒。**

转派成功后：

```
current_assignee_id = 新维修人员
status = 待接单
```

然后给新的维修人员重新生成接单截止时间。

这里建议把“转派申请”和“工单流转记录”分开：

- 转派申请表负责审批过程；
- 工单流转记录负责记录真正发生的负责人变化。

也就是说，申请被驳回时不会产生负责人变更；只有管理员审批通过且系统真正找到新负责人之后，才写：

```
原负责人：张师傅
新负责人：李师傅
操作类型：转派
转派来源：维修人员申请
```

# 十九、工单主表职责

工单主表只保存工单当前状态。

核心字段包括：

```
status
current_assignee_id
```

其中：

```
status
```

表示当前工单状态。

```
current_assignee_id
```

表示当前负责该工单的维修人员。

主表不负责完整保存历史负责人。



# 二十、维修员工时间方案表

> 同一时间段内所有维修人员执行统一上下班时间。

例如：

| 生效开始日期 | 生效结束日期 | 上班时间 | 下班时间 |
| ------------ | ------------ | -------- | -------- |
| 2026-05-01   | 2026-09-30   | 08:00    | 18:00    |
| 2026-10-01   | 2027-04-30   | 08:30    | 17:30    |

这样可以覆盖夏季、冬季作息。

表类似：

```
repair_work_schedule
```

核心字段：

```
id
schedule_name
start_date
end_date
work_start_time
work_end_time
enabled
create_time
update_time
```

例如：

```
夏季作息
2026-05-01
2026-09-30
08:00
18:00
```







# 二十一、工单流转记录

需要独立保存工单流转历史。

每发生一次：

```
状态变化
负责人变化
派单
接单
转派
中断
恢复
维修完成
返工
取消
```

都产生一条流转记录。

至少记录：

```
工单ID
原状态
新状态

原负责人
新负责人

操作人
操作类型
操作原因

操作时间
```

例如：

```
工单：WO202609160023

操作类型：转派

原状态：维修中
新状态：待接单

原负责人：张师傅
新负责人：李师傅

原因：需要其他工种

操作时间：
2026-09-19 14:20:00
```

因此即使主表：

```
current_assignee_id
```

不断发生变化，也可以完整追溯历史负责人。

# 二十二、工单状态

当前确定状态：

```
0 - 待派单
1 - 待接单
2 - 维修中
3 - 待确认
4 - 返工中
5 - 已中断
6 - 已完成
7 - 已取消
```

主要状态流转：

```
待派单
↓
待接单
↓
维修中
↓
待确认
↓
已完成
```

维修中断：

```
维修中
↓
已中断
↓
维修中
```

返工：

```
待确认
↓
返工中
↓
维修中
```

派单异常：

```
待派单
↓
自动派单失败
↓
仍保持待派单
↓
管理员人工处理
```

因此：

```
派单失败
转派失败
接单超时
维修超时
异常工单
疑似重复
```

均不需要额外设计为业务状态。

通过异常标记、截止时间、关联关系或者操作记录表达即可。

# 二十三、增加维修人员请假功能

```
维修人员提交请假申请
↓
填写请假开始时间、结束时间、原因
↓
管理员审批
   ↙          ↘
驳回          同意
 ↓             ↓
维持原状态     请假生效
               ↓
        维修人员状态 = 请假中
               ↓
       处理该人员未完成工单
```

建议维修人员状态至少有：

```
0 正常
1 请假中
2 停用
```

## 请假审批通过后，立即停止给该人员派新单

管理员审批通过以后，只要当前时间进入请假区间，该维修人员必须从自动派单候选人中排除。

即：

```
维修人员状态 = 请假中
```

自动派单：

```
故障类型匹配
↓
区域匹配
↓
过滤：
停用
请假中
不可接单
↓
继续派单
```

所以请假和派单逻辑天然关联。

## 请假期间未完成工单需要批量转派

这是此次新增里最重要的一点。

管理员审批请假后，需要检查该维修人员当前未完成的工单。

建议需要转出的主要是：

```
待接单
维修中
返工中
已中断
```

然后：

```
请假审批通过
↓
查找维修人员未完成工单
↓
逐单执行重新派单
```

每一张工单都单独匹配：

```
原工单故障类型
+
工单位置
+
其他维修人员负责范围
+
其他人员状态
+
当前工作量
```

找到合适人员：

```
转派
↓
新负责人进入待接单
```

找不到：

```
重新派单失败
↓
工单进入待人工派单
↓
通知管理员
```

这仍然遵守之前的底线：

> 任何自动转派失败，都必须显式进入管理员处理范围。

## 请假导致的转派和普通转派要区分来源

虽然最后都是“负责人变更”，但业务来源不同。

建议操作类型或转派来源记录为：

```
维修人员主动申请转派
维修人员请假自动转派
接单超时自动转派
管理员人工转派
```

以后查工单历史时就能知道：

```
为什么换人？
```

例如：

```
操作类型：自动转派
转派来源：维修人员请假
原负责人：张师傅
新负责人：李师傅
操作时间：2026-09-20 09:00
```

## 请假时间与已接单工单的一个边界需要这样定

例如：

```
维修人员请假：
9月22日 08:00
~
9月24日 18:00
```

但管理员在：

```
9月20日
```

就审批通过了。

这时候不建议马上把人员状态改成：

```
请假中
```

否则22日之前他都不能工作。

更合理的是区分：

```
请假已批准
```

和：

```
当前是否处于请假时间
```

也就是说：

```
当前时间 < leave_start
→ 人员仍然正常

leave_start <= 当前时间 <= leave_end
→ 请假中

当前时间 > leave_end
→ 自动恢复正常
```

这样维修人员状态其实最好不要完全靠人工维护字段。

可以保留：

```
status
```

表示：

```
正常 / 停用
```

而“请假中”根据有效请假单实时判断。

或者为了查询简单，在请假开始和结束时由定时任务更新状态。

第一阶段我更推荐后者：

```
请假开始
→ status = 请假中

请假结束
→ status = 正常
```

逻辑更直观。

------

## 请假工单转派的执行时间

不要在：

```
管理员审批通过
```

这一刻就全部转走。

例如：

```
今天9月20日审批
请假从9月25日开始
```

如果马上转派，那么他未来5天原本还能正常处理的工单也被转走了。

推荐：

> **在请假正式开始时，处理仍然未完成的工单。**

流程：

```
管理员提前审批
↓
请假状态 = 已通过
↓
到达请假开始时间
↓
维修人员状态改为请假中
↓
查找此时仍未完成的工单
↓
逐个自动转派
```

这样最合理。

如果请假：

```
立即生效
```

那审批通过后马上执行即可。

------

## 请假结束

请假结束时间到达：

```
请假结束
↓
维修人员状态：
请假中 → 正常
↓
重新进入自动派单候选范围
```

已经因为请假转给其他人的工单：

> 不自动转回来。

这一点要明确。

否则会出现：

```
张师傅请假
→ 工单转给李师傅
→ 李师傅已经开始维修
→ 张师傅回来
→ 又被系统转回
```

业务会非常混乱。

所以：

> **请假转派是一次正式负责人变更，不做自动回滚。**

------

## 现在派单候选人过滤规则可以正式定为

```
找到支持该故障类型的维修人员
↓
根据位置匹配负责区域
↓
排除：
  停用人员
  当前处于请假中的人员
  其他不可接单人员
↓
如果是转派：
  排除原负责人
↓
按照当前未完成工单数量升序
↓
选择第一人
↓
派单
```







# 二十四、完整业务链路

```
学生提交报修
        ↓
识别疑似重复报修
        ↓
确定故障类型
        ↓
匹配：
故障类型 + 负责区域
        ↓
自动派单
   ↙             ↘
成功             失败
 ↓                ↓
待接单        待人工派单
 ↓                ↓
维修人员接单      管理员处理
 ↓
维修中
 ├─────────────────┐
 ↓                 ↓
记录处理过程       维修中断
记录维修材料           ↓
 ↓                 等待条件恢复
 ↓                     ↓
 ↓                 恢复维修
 └─────────────────┘
 ↓
维修人员提交维修结果
 ↓

   ↙                 ↘
确认完成             申请返工
 ↓                       ↓

 ↓                       ↓

                         ↓

                   ↙           ↘
               普通返工       异常返工
                  ↓              ↓
              继续处理        管理员介入
```

## 完整异常链路

```
自动派单失败
→ 管理员兜底

接单超时
→ 自动重新派单
→ 失败则管理员兜底

维修人员主动申请转派
→ 管理员审批
→ 自动重新派单
→ 失败则管理员兜底

维修人员请假
→ 请假开始时自动转出未完成工单
→ 单张转派失败则管理员兜底

多次返工
→ 管理员介入

维修中断长期未恢复
→ 超时提醒管理员
```

核心原则：

> **自动派单负责处理正常流转，管理员负责所有自动流程无法完成的异常情况；任何工单始终必须处于“明确负责人”或“明确等待管理员处理”二者之一。**





# 二十五、系统审计原则

整个系统必须遵循：

> **每一个关键操作、状态变化、负责人变化都必须可以追溯。**

至少需要记录：

```
谁
在什么时间
对哪张工单
执行了什么操作
状态从什么变为什么
负责人从谁变成谁
为什么执行该操作
```

需要审计的典型事件包括：

```
学生提交报修
系统自动派单
管理员人工派单
维修人员接单
接单超时
系统自动转单
维修开始
维修中断
维修恢复
发起转派
转派成功
转派失败
提交维修结果
学生确认完成
学生申请返工
管理员异常介入
工单取消
工单完成
```

其中：

- **工单流转记录**负责记录工单生命周期；
- **系统操作日志**负责记录用户在系统中的操作行为。

两者职责不要完全混为一张表。

# 二十六、系统核心原则

整个系统最终遵循四个核心原则。

### 1. 工单不能失控

无论：

```
自动派单失败
自动转派失败
多次返工
异常中断
```

最终必须：

```
通知管理员
+
进入明确的管理员处理入口
```

### 2. 工单必须可追溯

任何状态和负责人变化都不能覆盖历史。

必须能够回答：

```
这张工单最开始派给谁？
谁接过单？
为什么被转派？
什么时候中断？
谁恢复的？
维修了几次？
为什么返工？
```

### 3. 超时不等于状态

接单超时和完成超时通过截止时间计算：

```
当前时间 > 截止时间
```

不额外把工单变成“超时状态”。

### 4. 自动化必须存在人工兜底

正常流程系统自动执行。

任何系统无法判断或者自动匹配失败的情况：

```
自动处理
↓
失败
↓
管理员人工处理
```

管理员是整个维修工单系统异常流程的最终兜底角色。





# 一、功能范围

本项目面向宿舍报修场景，角色包括**学生、维修人员、管理员**，围绕“报修—派单—接单—维修—确认—评价/返工”的完整闭环建设。

## 1. 用户与权限

系统支持三类角色：

- 学生：提交报修、查看本人工单、确认完成、申请返工、评价服务。
- 维修人员：接单、记录维修过程、登记材料、中断/恢复维修、提交维修结果、申请转派、申请请假。
- 管理员：管理基础配置、人工派单、审批转派、审批请假、处理异常工单、查看全部工单及审计记录。

系统通过 `sys_user` 统一记录账号和角色信息。

## 2. 学生报修

学生可以填写：

- 校区；
- 区域；
- 楼栋；
- 房间；
- 具体位置描述；
- 故障类型；
- 问题描述；
- 现场图片，可选；
- 联系人及联系方式。

系统生成唯一工单编号并记录报修时间。

## 3. 重复报修识别

学生提交前，系统检查：

> 同一校区 + 区域 + 楼栋 + 房间 + 故障类型，在24小时内是否存在未关闭工单。

未关闭状态包括：

- 待派单；
- 待接单；
- 维修中；
- 返工中；
- 已中断。

发现相似工单时提示学生，但**不强制禁止提交**。

## 4. 自动派单

系统按照以下顺序匹配维修人员：

```
故障类型匹配
↓
负责区域匹配
↓
排除停用、请假中、不可接单人员
↓
比较当前未完成工单数量
↓
优先派给负载最低人员
```

自动派单失败时，工单继续进入明确的管理员待处理范围，由管理员人工派单。

## 5. 接单与响应超时

系统派单后，维修人员原则上需要在**30分钟有效工作时间内**接单。

响应时间计算：

- 只累计维修工作时间；
- 下班时间不计入；
- 根据夏季、冬季等工作时间方案自动计算接单截止时间。

维修人员未按时接单时：

```
接单超时
↓
系统自动重新匹配维修人员
↓
重新派单
```

重新派单失败则通知管理员处理。

## 6. 接单与维修时限

维修人员接单时可以填写预计完成时间。

规则：

```
填写预计完成时间
→ complete_deadline = 预计完成时间

未填写
→ complete_deadline = 接单时间 + 24小时
```

系统分别在：

- 剩余10分钟；
- 剩余5分钟；
- 到达截止时间；

进行提醒。

“超时”作为计算结果，不额外设计成工单状态。

## 7. 维修过程记录

维修人员可以持续添加：

- 处理说明；
- 现场图片；
- 处理时间。

管理员和学生可以查看维修过程。

## 8. 维修材料记录

维修人员可登记：

- 材料名称；
- 规格；
- 数量；
- 单位；
- 使用时间；
- 备注。

管理员可查看材料明细。

学生端第一阶段默认不展示内部材料明细，只展示维修结果和处理说明。

## 9. 维修中断与恢复

维修人员可中断维修。

支持原因：

- 等待材料；
- 需要第三方介入；
- 现场条件不允许；
- 其他。

系统记录：

- 中断时间；
- 中断原因；
- 恢复时间。

业务状态：

```
维修中
→ 已中断
→ 维修中
```

## 10. 转派申请

维修人员不能直接转单，必须发起转派申请。

可选原因：

- 不属于本人负责范围；
- 不具备对应技能；
- 当前无法处理；
- 需要其他工种；
- 工作量过大；
- 其他。

流程：

```
维修人员申请
↓
管理员审批
├─ 驳回 → 原负责人继续处理
└─ 同意 → 系统自动重新匹配维修人员
                ↓
          成功 / 失败
```

自动转派失败时通知管理员，由管理员人工处理。

## 11. 维修人员请假

维修人员可以提交请假申请，包括：

- 开始时间；
- 结束时间；
- 请假原因。

管理员审批后，请假到达开始时间时：

```
维修人员 → 请假中
↓
停止进入自动派单候选池
↓
查找其未完成工单
↓
逐单自动重新派单
```

转派失败的工单进入管理员待处理范围。

请假结束后维修人员恢复正常状态，但此前已经转出的工单**不自动转回**。

## 12. 维修完成与学生确认

维修人员完成处理后提交维修结果，工单进入：

```
待确认
```

学生可以：

- 确认完成；
- 申请返工。

确认完成后进入评价流程。

## 13. 服务评价

学生完成确认后，可对维修服务进行评价，包括：

- 评分；
- 评价内容。

同一工单只能评价一次。

## 14. 返工

学生认为问题没有解决时，可以申请返工。

返工：

- 不创建新的独立工单；
- 原工单重新进入维修流程；
- 记录每一次返工原因和返工次数。

规则：

```
第一次返工
→ 原维修人员继续处理

第二次返工
→ 通知管理员预警

第三次及以上
→ 标记异常工单
→ 管理员必须介入
```

管理员可决定：

- 更换维修人员；
- 更换维修方案；
- 转第三方维修；
- 更换设备。

## 15. 异常工单处理

以下情况均需要管理员兜底：

- 自动派单失败；
- 接单超时重新派单失败；
- 转派审批通过后自动匹配失败；
- 请假导致工单重新分配失败；
- 多次返工；
- 其他无法自动处理的异常。

核心原则：

> 任何工单必须始终处于“已有明确负责人”或“明确等待管理员处理”两种情况之一。

## 16. 工单状态

第一阶段统一：

```
0 待派单
1 待接单
2 维修中
3 待确认
4 返工中
5 已中断
6 已完成
7 已取消
```

以下概念不是状态：

- 超时；
- 疑似重复；
- 派单失败；
- 转派失败；
- 异常工单。

## 17. 工单审计与操作日志

所有关键操作必须可追溯，包括：

- 创建工单；
- 自动派单；
- 人工派单；
- 接单；
- 接单超时转派；
- 主动转派；
- 请假转派；
- 维修中断；
- 恢复维修；
- 提交维修结果；
- 学生确认；
- 返工；
- 取消；
- 管理员异常介入。

系统分别维护：

- 工单流转记录：描述一张工单生命周期发生了什么；
- 系统操作日志：描述哪个用户执行了什么系统操作。

# 二、第一阶段非目标

第一阶段明确**不做或暂缓**以下功能，以保证核心维修闭环优先完成。

## 1. 不做复杂微服务架构

采用 Spring Boot 单体应用，不拆：

- 工单服务；
- 用户服务；
- 派单服务；
- 消息服务；

等独立微服务。

## 2. 不引入复杂消息中间件

第一阶段不强制使用：

- RocketMQ；
- RabbitMQ；
- Kafka。

超时和请假任务采用 Spring Scheduling 实现。

## 3. 不做复杂智能派单算法

第一阶段不做：

- AI派单；
- 权重评分模型；
- 距离最短算法；
- GIS实时位置；
- 历史评分综合推荐。

派单只依据：

> 故障类型 + 负责区域 + 人员可用状态 + 当前未完成工单数量。

## 4. 不做AI故障识别

不通过图片或文本自动识别：

- 故障类别；
- 故障严重程度；
- 所需维修方案。

故障类型由学生选择。

## 5. 不做完整库存管理

维修材料只记录实际使用情况。

第一阶段不实现：

- 库存数量；
- 出入库；
- 采购；
- 领料审批；
- 库存预警；
- 成本核算。

## 6. 不做复杂排班系统

第一阶段只维护一段时间内所有维修人员统一工作时间。

不实现：

- 每人独立班次；
- 轮班；
- 值夜班；
- 临时调班；
- 自动排班。

## 7. 不做复杂SLA规则引擎

只实现明确的：

- 30分钟有效工作时间接单时限；
- 预计完成时间或默认24小时完成时限。

不建设通用 SLA 配置平台。

## 8. 不做维修费用结算

第一阶段不涉及：

- 学生支付；
- 工时费用；
- 材料费用；
- 财务结算；
- 第三方供应商结算。

## 9. 不做实时定位

不跟踪维修人员GPS位置和行动轨迹。

## 10. 不做IoT自动报修

不接：

- 水电传感器；
- 智能门锁；
- 烟感；
- 设备监控平台。

## 11. 不做复杂实时通信

第一阶段允许通过轮询完成提醒。

SSE 可作为后续增强，不要求首版必须实现 WebSocket。

## 12. 不做完整第三方维修商管理

“转第三方维修”第一阶段作为管理员人工处理结果记录。

不建立供应商、合同、结算等完整体系。

# 三、总体验收标准

项目验收的核心目标是：

> 学生提交一张报修单后，系统能够可靠地完成自动派单、接单、维修、异常处理、学生确认及评价全过程，且所有负责人、状态和关键时间均可完整追溯。

# 四、分功能验收标准

## 1. 用户角色

验收通过条件：

- 学生只能操作本人报修相关功能；
- 维修人员只能处理自己负责的工单；
- 管理员可管理全部工单和审批事项；
- 不同角色访问未授权接口时必须被拒绝。

## 2. 学生报修

应满足：

- 可以正常填写结构化位置、故障类型、描述、联系方式；
- 图片为可选；
- 提交成功生成唯一工单号；
- 工单初始状态正确；
- 创建时间、报修人等数据正确落库。

## 3. 重复报修

准备：

- 同一房间；
- 同一故障类型；
- 24小时内已有未关闭工单。

验收：

- 新提交时系统能识别相似工单；
- 展示原工单编号；
- 学生可以取消提交；
- 学生也可以选择继续提交；
- 新工单能够记录疑似重复关系。

## 4. 自动派单

准备多个维修人员：

```
A：技能符合、区域符合、2个未完成工单
B：技能符合、区域符合、1个未完成工单
C：技能不符合
D：请假中
```

验收：

- C被过滤；
- D被过滤；
- 系统选择B；
- 工单进入待接单；
- 当前负责人正确；
- 派单时间和接单截止时间正确；
- 流转记录存在。

## 5. 自动派单失败

没有符合条件的维修人员时：

- 工单不能丢失；
- 工单保持待派单；
- 管理员能够在待人工派单列表看到；
- 管理员收到对应提醒；
- 管理员可以人工指定维修人员。

## 6. 有效工作时间

配置：

```
工作时间 08:00 - 18:00
17:50 派单
```

验收：

```
接单截止时间 = 次日08:20
```

不得计算成：

```
18:20
```

如果20:00派单，应从次日08:00开始累计。

## 7. 接单

维修人员接单后：

- 状态从待接单变为维修中；
- 记录接单时间；
- 填写预计完成时间时，截止时间等于预计完成时间；
- 未填写时，截止时间默认接单时间+24小时；
- 生成工单流转记录。

重复接单请求只能成功一次。

## 8. 接单提醒

达到：

```
剩余10分钟
剩余5分钟
截止时间
```

分别只产生一次提醒。

定时任务重复扫描不得产生重复消息。

## 9. 接单超时

超过接单截止时间仍未接单：

- 原负责人不再继续持有当前派单；
- 系统重新匹配其他维修人员；
- 新负责人重新获得完整接单时限；
- 流转历史中记录原负责人和新负责人；
- 如果找不到新人，自动进入管理员处理。

## 10. 维修过程

维修人员可以连续增加多条处理记录。

管理员和学生打开工单详情，可以按照时间顺序看到完整维修过程。

## 11. 维修材料

维修人员可以登记多个材料。

管理员可以查看：

- 材料名称；
- 规格；
- 数量；
- 单位；
- 使用时间。

学生默认不显示内部材料明细。

## 12. 维修中断

维修人员可：

```
维修中 → 已中断
```

同时必须填写中断原因。

恢复后：

```
已中断 → 维修中
```

系统能够追溯中断时间和恢复时间。

## 13. 转派申请

维修人员提交转派申请后：

- 当前负责人不能立即发生变化；
- 管理员能看到待审批申请。

管理员驳回：

- 工单负责人不变。

管理员通过：

- 系统自动重新派单；
- 原负责人必须从候选人中排除。

转派成功：

- 新负责人正确；
- 状态回到待接单；
- 重新计算接单截止时间。

转派失败：

- 管理员收到异常提醒；
- 工单不能进入无人管理状态。

## 14. 请假

维修人员提交请假申请后：

- 管理员可审批；
- 审批通过但尚未到开始时间时，维修人员仍可正常工作；
- 到请假开始时间，人员自动进入请假中；
- 自动派单不再选择该人员。

## 15. 请假工单转移

请假开始时：

- 查询该人员全部未完成工单；
- 每张工单分别重新匹配维修人员；
- 可以分别派给不同人员；
- 每次负责人变化都有流转记录；
- 无法重新派出的工单通知管理员。

请假结束：

- 维修人员恢复正常；
- 已经转出的工单不得自动转回。

## 16. 完成超时

在预计完成时间：

```
剩余10分钟
剩余5分钟
到期
```

分别能够提醒。

到期以后：

- 工单原业务状态不自动变成“超时”；
- 管理员能够识别该工单已超时。

## 17. 提交维修完成

维修人员提交维修结果后：

```
维修中 → 待确认
```

并记录：

- 完成说明；
- 完成图片，可选；
- 提交时间。

学生可以查看维修结果。

## 18. 学生确认

学生点击确认后：

```
待确认 → 已完成
```

记录：

- 确认时间；
- 最终完成时间。

已完成工单不得再次执行维修中的业务动作。

## 19. 评价

完成工单：

- 学生可以评分并填写评价；
- 一个工单只能产生一次最终评价；
- 重复提交不能产生两条评价。

## 20. 第一次返工

学生申请第一次返工：

- 不创建新的独立工单；
- 原工单 `rework_count + 1`；
- 生成返工记录；
- 原维修人员继续负责；
- 原工单重新进入维修流程。

## 21. 第二次返工

第二次返工后：

- `rework_count = 2`；
- 管理员收到异常预警；
- 工单历史完整保留。

## 22. 第三次及以上返工

达到第三次：

- `exception_flag = 1`；
- 工单进入管理员异常工单列表；
- 必须允许管理员人工介入；
- 管理员可以重新指定人员或记录其他处理方案。

## 23. 审计追溯

任意选择一张完整流转过的工单，应能够查到：

```
谁提交的
什么时候提交
第一次派给谁
什么时候接单
是否发生过超时
是否转派
原负责人是谁
新负责人是谁
为什么转派
是否中断
何时恢复
维修人员做了什么
使用了什么材料
提交了几次完成
返工了几次
谁最终确认
什么时候完成
```

如果任一关键状态或负责人变化无法解释，则审计验收不通过。

# 五、核心验收场景

最终系统至少需要完整跑通以下五条端到端测试链路。

### 场景A：正常维修

```
学生报修
→ 自动派单
→ 维修人员接单
→ 维修
→ 提交完成
→ 学生确认
→ 评价
→ 已完成
```

### 场景B：接单超时

```
报修
→ 派给A
→ A超时
→ 自动派给B
→ B接单
→ 完成
```

### 场景C：主动转派

```
A接单
→ A申请转派
→ 管理员通过
→ 系统派给B
→ B处理完成
```

### 场景D：维修人员请假

```
A持有多个未完成工单
→ 请假审批通过
→ 请假开始
→ A进入请假中
→ 工单分别自动重新派给其他人员
→ 失败工单管理员处理
```

### 场景E：多次返工

```
维修完成
→ 学生第一次返工
→ 再次维修
→ 第二次返工
→ 管理员预警
→ 第三次返工
→ 异常工单
→ 管理员介入
```

只要这五条主链路都稳定跑通，并且数据、状态、负责人和审计记录全部正确，第一阶段核心业务即可认为通过验收。

# 六、项目第一阶段完成定义

第一阶段可以定义为：

> 系统完成学生报修、重复识别、自动/人工派单、维修人员接单与维修处理、超时提醒、转派审批、维修人员请假及工单重分配、维修中断、维修材料、学生确认、返工、服务评价和异常工单管理，并能够对工单全过程的状态、负责人和处理时间进行完整追溯；任何自动派单或异常处理失败均能够进入管理员人工兜底流程。

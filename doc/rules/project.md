# 项目开发规则

## 一、项目定位

本项目为宿舍报修系统，采用前后端分离的单体架构。系统面向学生、维修人员和管理人员，具体业务范围、角色权限与验收标准以 `doc/requirements/` 中已确认的文档为准。

在需求尚未确认时，不得自行虚构业务流程、接口字段、数据状态、权限范围或定时任务规则。

## 二、技术栈

### 2.1 前端

- 基础框架：Vue 3、Vite。
- 学生端与维修人员端组件库：Vant。
- 管理端组件库：Element Plus。
- 状态管理：Pinia。
- 路由管理：Vue Router。
- 接口请求：Axios。

### 2.2 后端

- Java 版本：Java 17 或更高版本。
- 基础框架：Spring Boot 3。
- Web 层：Spring MVC。
- 身份认证与授权：Spring Security、JWT。
- 数据访问：MyBatis。
- 参数校验：Hibernate Validator。
- 定时任务：Spring Scheduling。

### 2.3 基础设施

- 关系型数据库：MySQL 8，用于持久化工单及业务数据。
- 缓存与并发控制：Redis，用于缓存、并发控制和提醒去重。
- 对象存储：MinIO，用于存储报修图片和维修现场图片。
- 部署方式：Nginx、Docker Compose。
- 实时通知：当前不作为基础能力强制实现；后续确有需求时可扩展 SSE。

## 三、架构约束

1. 前端与后端通过明确的 HTTP 接口契约通信，不共享运行时状态。
2. 后端保持单体部署，按业务职责划分模块，不提前拆分微服务。
3. 控制器负责接收请求、参数校验和返回结果，不承载核心业务逻辑。
4. 业务规则放在服务层，数据访问通过 MyBatis 映射层完成。
5. MySQL 是业务数据的最终事实来源；Redis 不作为不可恢复业务数据的唯一存储。
6. 图片文件存入 MinIO，数据库只保存对象标识、访问所需元数据及业务关联。
7. 接单超时、完成超时、请假生效和自动转派等任务由 Spring Scheduling 执行；具体触发条件必须来源于已确认需求。
8. 新增基础设施或技术组件前，应先说明现有技术栈无法满足的具体问题，并更新架构文档。

## 四、文档规则

1. 原始需求、范围变更和验收标准记录在 `doc/requirements/`。
2. 系统边界、模块关系、数据流和关键技术决策记录在 `doc/architecture/`。
3. 接口路径、请求参数、响应结构、错误码和权限要求记录在 `doc/api/`。
4. 表结构、字段含义、索引、约束和迁移说明记录在 `doc/database/`。
5. 身份认证、授权模型、敏感数据和安全边界记录在 `doc/security/`。
6. 数据库或中间件的专项约束记录在 `doc/rules/addons/`。
7. 文档内容使用中文；代码标识符、协议名称和技术产品名称可保留英文。
8. 需求、接口和数据结构发生变化时，相关文档应与代码在同一任务中更新。
9. 在完成每一阶段的任务后，要在doc/verify/中维护各阶段工作的验收记录。
10. 总的前端联调接口说明维护在 `doc/api/前端联调接口说明.md`；每新增或变更一个接口，必须在同一任务中同步更新该文档。


## 五、开发规则

1. 一次只处理一个可验证的任务，不顺带修改无关文件。
2. 优先遵循项目已有结构和命名习惯；尚无约定时，先在文档中明确再实现。
3. 前后端公共数据结构应以接口契约为准，避免分别维护含义不一致的字段。
4. 所有外部输入均需校验；后端不得仅依赖前端校验。
5. 权限判断必须在后端执行，前端的页面和按钮控制只用于改善交互体验。
6. 异常响应应使用统一结构，不向客户端暴露堆栈、密钥、内部路径或数据库细节。
7. 配置通过环境变量或受控配置文件注入，不将密码、令牌、密钥及真实生产数据写入代码或测试。
8. 删除、覆盖、推送、部署及不可逆的数据迁移执行前，必须获得明确确认。
9. 代码只保留在本地或公司内部仓库，不推送至外部平台。

## 六、验证规则

每次变更应根据影响范围执行验证，并在交付说明中列出：

- 修改了什么。
- 使用什么命令或方式进行了验证，以及验证结果。
- 哪些内容尚未完成或未验证。

测试通过只代表既定检查通过，还应对照需求和验收标准确认实现是否满足目标。

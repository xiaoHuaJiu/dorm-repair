# 请假生效与转派设计

> **状态：开发完成，暂未测试。** 项目当前无法启动，本文描述的设计未经过运行时验证。

本文描述 PLAN-9（维修人员请假）的领域模型、生效/结束链路、并发与幂等设计。与《自动派单与异步补偿设计.md》共同构成派单体系的完整视图。

## 1. 领域模型

请假复用既有表 `repair_leave_request`，双状态字段分离「审批」与「生效处理」两件事：

| 字段 | 含义 | 取值 |
|---|---|---|
| `status` | 审批状态 | 0 待审批 / 1 已通过 / 2 已驳回 |
| `reassign_status` | 转派处理状态 | 0 未处理 / 1 处理中 / 2 已完成 / 3 部分失败 |
| `start_time` / `end_time` | 请假时间段，语义 `[startTime, endTime)` | — |
| `review_admin_id` / `review_remark` / `review_time` | 审批人与审批结果 | — |

审批通过只代表管理员同意；请假是否开始由生效定时任务按时间判断。维修人员当前状态记录在 `repair_worker.work_status`：`0 正常 / 1 请假中 / 2 停用`。

## 2. 状态机

### 2.1 审批状态

```
创建 → 0 待审批 ──APPROVE──→ 1 已通过
                └──REJECT───→ 2 已驳回（终态，不占用时间段）
```

### 2.2 转派处理状态（仅已通过请假参与）

```
0 未处理 ──CAS 抢占──→ 1 处理中 ──全部成功──→ 2 已完成
                                 └─部分失败──→ 3 部分失败
1 处理中且超时（update_time < now - staleMinutes）→ 允许再次抢占，1→1
```

## 3. 提交与审批链路

### 3.1 提交请假申请

```
前端 bizNo → LeaveRequestService.create
  ├─ 解析当前维修人员（登录上下文）
  ├─ 请求摘要（bizNo 内容哈希）
  ├─ 幂等重放：sys_idempotent_record 已成功 → 返回首次结果快照
  ├─ Redis 门闩（setIfAbsent，TTL 10 分钟）：拿不到且无成功记录 → 409 处理中
  ├─ 时间校验：start < end 且 end > now
  ├─ 重叠校验：countOverlap（仅 0 待审批 / 1 已通过，[start,end) 半开区间）
  └─ LeaveTransactionService.createLeave（同事务）：
       幂等记录(status=0) + 请假记录 + 操作日志 → markSuccess 快照
```

Redis 不可用时门闩降级为 MySQL 幂等唯一约束（`sys_idempotent_record` 的 `biz_type + user_id + biz_no` 唯一键），捕获 `DuplicateKeyException` 后回放快照。

### 3.2 审批请假

```
LeaveReviewService.review
  ├─ 幂等：Redis 门闩 + 幂等记录，机制同提交
  └─ LeaveTransactionService.reviewLeave（同事务）：
       幂等记录 + selectByIdForUpdate 行锁 → 校验待审批 → casReview 条件更新
       （WHERE status = 期望值，并发审批只有一个成功）+ 操作日志 → markSuccess
```

并发审批靠 `casReview` 数据库条件更新保证原子性：两个管理员同时审批只有一人返回成功，另一人收到 409。

## 4. 请假生效链路（RepairLeaveEffectiveTask）

每分钟执行，无整体大事务，各步骤独立提交，允许部分成功：

```
selectEffectiveIds：status=1 AND start_time<=now AND end_time>now
                    AND (reassign_status=0 OR (reassign_status=1 AND update_time<staleBefore))
  └─ processOne（逐单）：
     1. casTakeForEffective：reassign_status 0→1（或超时 1→1），CAS 抢到才继续
     2. 校验仍未结束；已结束则闭环 1→2 后返回
     3. workers.casUpdateStatus(NORMAL → ON_LEAVE)：停用人员不被覆盖；CAS 未命中时继续后续转派
     4. 写系统操作日志（SYSTEM，roleType=4）
     5. selectOpenOrderIdsByAssignee：状态 IN (1,2,4,5) 的未完成工单
     6. 逐单 RepairDispatchService.dispatch(orderId, {workerId}, LEAVE_REASSIGN)
        —— 单工单异常隔离；派单服务内部失败时工单 casMarkPending → 待派单 + 单工单告警
     7. 汇总：failed=0 → reassign_status 2；否则 3；汇总提醒仅在本次终态 CAS 成功闭环时写入
        （order_id=NULL，source_type=4，failure_reason=LEAVE_REASSIGN_PARTIAL_FAILED）
```

### 4.1 处理中超时补偿

`reassign_status=1` 表示任务已被抢占但未闭环。正常情况下扫描条件只取 `reassign_status=0`；若处理中超过 `app.leave.stale-minutes`（默认 5 分钟）未推进（`update_time` 未变），视为进程中断，允许重新抢占（CAS 条件放宽为 `update_time < staleBefore`）。

恢复执行是幂等的：

- `work_status` 更新为幂等更新；
- 转派时重新查询仍属于请假人员的未完成工单——已成功转走的工单负责人已变更，不会重复转派；
- 派单服务对 `LEAVE_REASSIGN` 来源内置双重防线：派单前校验工单仍属于请假人员，CAS 未命中时重查工单，已不属于请假人员的工单视为已处理成功，不会重复转派也不会误报失败；
- 重复写操作日志的风险可接受（每次抢占最多一条）。

### 4.2 自动派单的双保险

- 生效任务先把人员置为请假中；
- `RepairDispatchService.selectDispatchCandidates` 的候选 SQL 本身过滤正在请假的员工。两道防线保证请假人员不会在请假期间被派新单。

## 5. 请假结束链路（RepairLeaveEndTask）

每分钟执行：

```
selectWorkerIdsWithEndedLeave：DISTINCT worker_id，status=1 AND end_time<=now
                              JOIN repair_worker 且 work_status=1（仅扫当前请假中的人员，避免 LIMIT 饥饿）
  └─ restoreWorker（逐人）：
     1. worker 必须当前为请假中，否则跳过
     2. countActiveLeave(workerId, now) > 0 → 连续请假，保持请假中
     3. casUpdateStatus(ON_LEAVE → NORMAL)：CAS 成功才继续，防止并发重复恢复
     4. 写系统操作日志（SYSTEM）
```

连续请假场景：请假 A 已结束、请假 B 仍生效时，A 的结束任务不会把人员恢复为正常；B 结束后再由其结束任务恢复。

## 6. 事务边界

| 步骤 | 事务 | 说明 |
|---|---|---|
| 创建请假 | 单事务 | 幂等记录 + 请假记录 + 操作日志 |
| 审批请假 | 单事务 | 幂等记录 + 行锁 + CAS + 操作日志 |
| 生效抢占 | 单条 CAS UPDATE | 独立提交，可重入 |
| work_status 更新 | 单条 CAS UPDATE（正常→请假中） | 幂等，停用人员不被覆盖 |
| 逐单转派 | 派单服务自有事务 | 每张工单独立提交，失败隔离 |
| 终态汇总 | 单条 CAS UPDATE | 独立提交；提醒仅在本次 CAS 成功时写入 |
| 汇总提醒 | 单条 INSERT | 失败仅记日志，不影响主流程 |

不设计覆盖全链路的巨型事务：抢占与转派之间无一致性依赖，全部原子化会放大锁范围并降低可用性。

## 7. 运维关注点

- 转派失败的工单进入待人工派单池，同时生成单工单告警与请假级汇总提醒，管理员可在异常工单页处理。
- 处理中超时补偿的 `stale-minutes` 应大于生效任务单轮最大耗时，避免正常执行被误判为中断。
- 请假人员恢复后不会自动接回旧工单；旧工单已由派单服务转给其他人员。

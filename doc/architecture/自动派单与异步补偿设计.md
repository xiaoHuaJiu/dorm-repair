# 自动派单与异步补偿设计

## 调用链

学生报修创建事务在提交前发布 `RepairOrderCreatedEvent`，监听器仅在事务成功提交后触发。监听器把工单 ID 投递到独立的有界 `dispatchTaskExecutor`，异步调用统一的 `RepairDispatchService`。创建事务和派单事务相互独立，派单失败不会回滚已经创建的工单。

## 匹配与并发

派单按技能、负责区域、人员账号与工作状态、有效请假和本轮排除人员进行批量过滤，通过一次聚合查询取得未完成工单工作量，并按“工作量升序、维修人员 ID 升序”选择。最终更新使用工单 ID、来源状态和原负责人作为 CAS 条件；工单更新与 `repair_order_flow` 写入处于同一事务，不使用 Redis 全局锁。

## 工作时间

接单截止时间累计 30 分钟有效工作时间。启用的 `repair_work_schedule` 决定每日上下班时间；`repair_holiday_calendar` 的放假日和调休上班日配置优先于普通周末判断。算法支持跨下班、跨日、跨周和跨工作方案，最多搜索 366 天，配置不足时按 `NO_WORK_SCHEDULE` 失败，禁止降级为自然时间加 30 分钟。

## 失败与恢复

派单失败后通过 CAS 将工单保持或恢复为待派单并清空负责人，向 `repair_dispatch_alert` 写入去重告警。同一工单、来源、失败原因和待处理状态只保留一条告警，重复发生只更新次数和最近发生时间。定时任务扫描超过 1 分钟仍待派单且无负责人的工单，重新提交异步派单；因此线程池拒绝、应用重启或进程在提交后退出都可由数据库状态恢复。

## 线程池参数

核心线程数、最大线程数、队列容量、补偿间隔、首次补偿延迟、批次大小和滞后时间均通过 `app.dispatch` 配置，并支持对应环境变量覆盖。线程池关闭时最多等待 30 秒完成已有任务。

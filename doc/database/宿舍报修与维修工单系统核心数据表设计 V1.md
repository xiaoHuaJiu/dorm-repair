# 宿舍报修与维修工单系统核心数据表设计 V1

> 位置层级补充：`repair_area.area_type` 取值为 1单位/校区、2区域、3楼栋、4房间；房间的 `parent_id` 指向楼栋，`repair_order.room_id` 指向房间节点。

## 一、整体表结构

### 核心业务表

```
1. repair_order                  工单主表
2. repair_work_schedule          维修人员工作时间方案表
3. repair_leave_request          维修人员请假申请表
4. repair_transfer_request       工单转派申请表
5. repair_process_record         维修过程记录表
6. repair_material_usage         维修材料使用记录表
7. repair_rework_record          返工记录表
8. repair_order_flow             工单流转记录表
9. sys_operation_log             系统操作日志表
```

### 必要支撑表

```
10. repair_fault_type             故障类型表
11. repair_worker                 维修人员扩展表
12. repair_worker_fault_type      维修人员-故障类型关联表
13. repair_worker_area_scope      维修人员负责区域表
14. sys_user                      系统用户表
15. repair_area                   区域表
16. repair_evaluation             学生评价表
17. repair_reminder_record        用于 10 分钟、5 分钟、0 分钟提醒的**防重复发送**。否则定时任务每扫描一次都可能重复提醒。
```



# 二、工单主表 `repair_order`

这是整个系统的核心表，只保存：

> 当前工单最新状态 + 当前负责人 + 当前关键时间节点。

历史变化全部放到 `repair_order_flow`。

## 状态

```
0 待派单
1 待接单
2 维修中
3 待确认
4 返工中
5 已中断
6 已完成
7 已取消
```

这里尤其注意：

```
超时
自动派单失败
转派失败
疑似重复
异常工单
```

全部**不是 status**。

## 为什么保存这些时间

### `dispatch_time`

记录当前这一轮派单是什么时候发生的。

### `accept_deadline`

派单成功时就算好：

```
有效工作时间30分钟后的时间点
```

例如：

```
工作时间 08:00 - 18:00

17:50派单

17:50 - 18:00 = 10分钟
次日08:00继续

accept_deadline = 次日08:20
```

提醒任务以后直接查：

```
accept_deadline
```

不用反复计算工作时间。

### `expected_complete_time`

维修人员接单时填写：

```
预计完成时间
```

### `complete_deadline`

如果填写了：

```
complete_deadline = expected_complete_time
```

否则：

```
complete_deadline = accept_time + 24小时
```

因此实际超时判断统一使用：

```
complete_deadline
```

## 审批状态

```

1 已通过
2 已驳回
3 已撤回
```

## `reassign_status`

这是一个比较重要的字段，用来防止定时任务重复执行请假转派：

```
0 未执行
1 执行中
2 已完成
3 部分失败
```

例如：

```
张师傅9月25日开始请假

9月20日管理员审批通过
```

此时：

```
status = 1
reassign_status = 0
```

9月25日真正进入请假时：

```
worker.status = 请假中

reassign_status:
0 → 1
```

开始转工单。

处理完：

```
reassign_status = 2
```

如果部分工单无法找到新负责人：

```
reassign_status = 3
```

同时通知管理员。

# 十、维修过程记录表 `repair_process_record`

用于记录维修全过程。

不是只记录最后一句：

> 已维修完成。

而是允许多条。

## 字段

| 字段                  | 类型          | 说明         |
| --------------------- | ------------- | ------------ |
| id                    | BIGINT        | 主键         |
| order_id              | BIGINT        | 工单ID       |
| worker_id             | BIGINT        | 操作维修人员 |
| record_type           | TINYINT       | 过程记录类型 |
| content               | VARCHAR(1000) | 过程内容     |
| image_urls            | JSON / TEXT   | 现场图片     |
| interrupt_reason_type | TINYINT       | 中断原因     |
| record_time           | DATETIME      | 记录时间     |
| create_time           | DATETIME      | 创建时间     |
| deleted               | TINYINT       | 逻辑删除     |

## `record_type`

```
1 普通维修记录
2 维修中断
3 恢复维修
4 提交维修结果
```

这样不需要再额外拆一张“维修中断表”。

## 中断原因

只有：

```
record_type = 2
```

时有效。

```
1 等待材料
2 需要第三方介入
3 现场条件不允许
4 其他
```

例如：

```
order_id = 1001
record_type = 2
content = 仓库暂无对应阀芯
interrupt_reason_type = 1
record_time = 14:20
```

恢复：

```
record_type = 3
content = 材料已领取，恢复维修
record_time = 16:00
```

于是：

```
中断时间
中断原因
恢复时间
```

全部都可以从维修过程记录中得到。

第一次：

```
1
```

```
2
```

```
3
```

```

```


# 十三、工单流转记录表 `repair_order_flow`

这是整个系统另一张最重要的表。

它负责回答：

> 这张工单到底发生过什么？

## 字段

| 字段                 | 类型         | 说明           |
| -------------------- | ------------ | -------------- |
| id                   | BIGINT       | 主键           |
| order_id             | BIGINT       | 工单ID         |
| operation_type       | TINYINT      | 工单操作类型   |
| from_status          | TINYINT      | 原状态         |
| to_status            | TINYINT      | 新状态         |
| original_assignee_id | BIGINT       | 原负责人       |
| new_assignee_id      | BIGINT       | 新负责人       |
| operator_id          | BIGINT       | 操作用户       |
| operator_role        | TINYINT      | 操作者角色     |
| source_type          | TINYINT      | 流转来源       |
| related_business_id  | BIGINT       | 对应业务记录ID |
| reason               | VARCHAR(500) | 原因           |
| operation_time       | DATETIME     | 操作时间       |
| create_time          | DATETIME     | 创建时间       |

## `operation_type`

可以定义：

```
1  创建工单
2  自动派单
3  人工派单
4  维修人员接单
5  自动转派
6  管理员转派
7  维修中断
8  恢复维修
9  提交维修结果
10 学生确认完成
11 申请返工
12 进入返工
13 取消工单
14 请假导致转派
15 接单超时转派
```

## `source_type`

用来进一步说明负责人为什么变化：

```
1 正常派单
2 接单超时
3 转派申请
4 维修人员请假
5 管理员人工处理
6 返工
7 系统自动处理
```

## `related_business_id`

非常有用。

例如某次负责人变化是因为：

```
转派申请 #888
```

则：

```
source_type = 转派申请
related_business_id = 888
```

如果因为：

```
请假申请 #200
```

则：

```
source_type = 维修人员请假
related_business_id = 200
```

这样从工单历史可以反查具体业务。

# 十五、关键关系总览

核心关系：

# 十六、功能一：学生提交报修时各表如何联动

## 流程

```
学生提交
↓
检查重复报修
↓
创建工单
↓
自动派单
```

### 第一步：查 `repair_order`

条件：

```
campus_id
area_id
building_id
room_id
fault_type_id
```

并且：

```
report_time >= 当前时间 - 24小时
```

状态属于：

```
待派单
待接单
维修中
返工中
已中断
```

发现：

```
WO202609160023
```

提示：

> 当前位置存在相似未完成工单。

如果学生仍提交：

### 第二步：插入 `repair_order`

```
status = 待派单
duplicate_flag = 1
duplicate_order_id = 原工单
```

### 第三步：插入 `repair_order_flow`

```
操作 = 创建工单
```

### 第四步：记录 `sys_operation_log`

```
学生提交报修
```

# 十七、功能二：系统自动派单

读取：

```
repair_order.fault_type_id
repair_order.campus_id
repair_order.area_id
repair_order.building_id
```

### 第一步

通过：

```
repair_worker_fault_type
```

找到会维修该类型的人。

### 第二步

通过：

```
repair_worker_area_scope
```

过滤负责范围。

### 第三步

通过：

```
repair_worker.status
```

排除：

```
请假中
停用
```

### 第四步

统计：

```
repair_order.current_assignee_id
```

下每个人的：

```
未完成工单数量
```

选择最少的人。

### 第五步

读取：

```
repair_work_schedule
```

根据当前日期找到对应：

```
上下班时间
```

计算：

```
accept_deadline
```

### 第六步更新 `repair_order`

```
status = 待接单
current_assignee_id = 李师傅
dispatch_time = 当前时间
accept_deadline = 计算后的时间
```

### 第七步插入 `repair_order_flow`

```
待派单 → 待接单
原负责人 NULL
新负责人 李师傅
操作类型 自动派单
```

如果失败：

```
repair_order.status
```

仍然：

```
待派单
```

并通知管理员。

# 十八、功能三：维修人员接单

维修人员点击接单。

更新：

```
repair_order
status:
待接单 → 维修中

accept_time = 当前时间
```

如果维修人员填写：

```
expected_complete_time
```

则：

```
complete_deadline = expected_complete_time
```

否则：

```
complete_deadline = accept_time + 24小时
```

然后插入：

```
repair_order_flow
待接单 → 维修中
操作 = 接单
```

# 十九、功能四：接单超时自动转派

定时任务扫描：

```
status = 待接单
AND accept_deadline <= 当前时间
```

找到超时工单。

然后重新执行：

```
自动派单算法
```

但：

```
排除原维修人员
```

成功：

```
repair_order.current_assignee_id
→ 新维修人员
```

重新计算：

```
dispatch_time
accept_deadline
```

插入：

```
repair_order_flow
操作类型：接单超时转派
原负责人：张
新负责人：李
```

失败：

```
status仍然待派单/进入待管理员处理范围
```

通知管理员。

# 二十、功能五：维修过程记录

维修人员每次填写过程：

```
repair_process_record
```

例如：

工单主表一般不需要更新。

因此一张工单：

```

```

# 二十一、功能六：维修中断与恢复

维修人员选择：

```
等待材料
```

插入：

```
repair_process_record

```

同时：

```
repair_order.status
维修中 → 已中断
```

然后：

```

```

记录：

```
维修中 → 已中断
```

```
repair_process_record

```


# 二十二、功能七：维修材料记录

# 二十三、功能八：维修人员提交完成

```

维修中 → 待确认

```

```
repair_order_flow
维修中 → 待确认
```

# 二十四、功能九：学生确认完成

学生确认：

更新：

```
repair_order
```

然后：

记录：

# 二十五、功能十：学生申请返工

学生没有确认完成，而是点击：

```
申请返工
```

### 第一步

插入：

```
repair_rework_record
```

例如：

```
order_id = 100
rework_no = 1
reason = 维修后仍然漏水
```

### 第二步

更新：

```
repair_order
rework_count = rework_count + 1
status = 返工中
```

第一次：

```
继续原维修人员
```

然后再进入：

```
维修中
```

### 第三步

写：

```
repair_order_flow
待确认 → 返工中
```

# 二十六、第二次、第三次返工联动

如果：

```
rework_count = 2
```

则：

```
repair_rework_record
+
通知管理员
```

如果：

```
rework_count >= 3
```

更新：

```
repair_order.exception_flag = 1
```

同时：

```
repair_rework_record.admin_intervention = 1
```

通知管理员人工介入。

管理员决定：

```
更换维修人员
更换维修方案
转第三方
更换设备
```

相应操作全部继续写：

```
repair_order_flow
```

# 二十七、功能十一：维修人员主动申请转派

维修人员发起：

```
repair_transfer_request
```

此时：

```
repair_order
```

**暂时不变。**

原负责人继续是：

```
current_assignee_id
```

等待管理员审批。

## 管理员驳回

只更新：

```
repair_transfer_request.approval_status = 已驳回
```

工单不变。

## 管理员同意

更新：

```
approval_status = 已通过
execute_status = 执行中
```

然后系统重新跑：

```
故障类型
+
负责区域
+
人员状态
+
工作量
```

并排除：

```
original_assignee_id
```

## 找到新人

更新：

```
repair_transfer_request
execute_status = 转派成功
new_assignee_id = 新维修人员
```

同时更新：

```
repair_order
current_assignee_id = 新人
status = 待接单
dispatch_time = 当前时间
accept_deadline = 新计算时间
```

然后：

```
repair_order_flow
```

记录负责人变化。

## 找不到新人

```
repair_transfer_request.execute_status
= 转派失败
```

记录：

```
failure_reason
```

工单进入管理员待处理范围，并通知管理员。

# 二十八、功能十二：维修人员申请请假

维修人员提交：

```
repair_leave_request
```

管理员审批。

审批通过后：

```
status = 已通过
```

但如果：

```
leave_start > 当前时间
```

暂时不影响：

```
repair_worker.status
```

# 二十九、功能十三：请假真正开始

定时任务发现：

```
已审批
AND start_time <= 当前时间
AND end_time > 当前时间
AND reassign_status = 0
```

则：

### 第一步

更新：

```
repair_worker.status
正常 → 请假中
```

### 第二步

更新：

```
repair_leave_request.reassign_status
0 → 1
```

### 第三步

查询该维修人员：

```
repair_order.current_assignee_id = worker_id
```

并且：

```
status IN (
待接单,
维修中,
返工中,
已中断
)
```

得到全部未完成工单。

### 第四步

一张一张重新派单。

# 三十、请假工单转派

例如张师傅有：

```
工单A
工单B
工单C
```

不是：

```
统一找一个人全部接收
```

而是分别根据：

```
工单自己的故障类型
+
自己的位置
```

独立重新匹配。

结果可能：

```
A → 李师傅
B → 王师傅
C → 无人符合
```

于是：

```
A/B 正常转派
```

分别写：

```
repair_order_flow
source_type = 维修人员请假
related_business_id = leave_request.id
```

C：

```
自动转派失败
→ 通知管理员
```

最终：

```
repair_leave_request.reassign_status
```

如果全部成功：

```
2 已完成
```

如果部分失败：

```
3 部分失败
```

# 三十一、功能十四：请假结束

定时任务：

```
end_time <= 当前时间
```

更新：

```
repair_worker.status
请假中 → 正常
```

恢复进入自动派单候选池。

之前已经转派出去的工单：

```
不转回来。
```

# 三十二、功能十五：完成超时提醒

定时任务查询：

```
status IN (
维修中,
返工中,
已中断
)
```

并比较：

```
complete_deadline
```

分别在：

```
剩余10分钟
剩余5分钟
到期
```

发送提醒。

但：

```
repair_order.status
```

不会因为超时发生变化。

仍然保持真实业务状态。

# 三十四、最终职责划分

## `repair_order`

负责：

> 现在怎么样。

## `repair_order_flow`

负责：

> 以前发生过什么。

## `repair_process_record`

负责：

> 维修人员实际做了什么。

## `repair_transfer_request`

负责：

> 为什么申请换维修人员、管理员是否同意。

## `repair_leave_request`

负责：

> 维修人员为什么在某段时间不能接单。

## `repair_rework_record`

负责：

> 为什么重新维修、已经返工多少次。

## `repair_material_usage`

负责：

> 维修用了什么。

## `repair_work_schedule`

负责：

> 什么时间算维修人员有效工作时间。

## `sys_operation_log`

负责：

> 哪个用户在系统里执行了什么操作。

## `sys_idempotent_record`（阶段 4 新增）

正式创建报修采用 Redis 与 MySQL 双层幂等。本表使用 `(biz_type,user_id,biz_no)` 唯一约束兜底，保存 `request_hash`、处理状态和成功结果最小快照。`request_hash` 不包含 `confirmDuplicate`，从而允许疑似重复确认使用原 `bizNo` 完成 `false → true` 流程。

## `repair_holiday_calendar`（阶段 5 新增）

保存法定放假日与调休上班日，为接单截止时间的有效工作时间计算提供最终日期依据。

## `repair_dispatch_alert`（阶段 5 新增）

保存自动派单失败待办。同一工单、来源、失败原因和处理状态通过唯一约束去重，定时补偿反复失败时累计发生次数，不重复制造相同待办。

共：

> **20 张正式业务/支撑表。**

其中真正围绕单张工单展开的核心表只有：

```
repair_order
repair_process_record
repair_material_usage
repair_rework_record
repair_transfer_request
repair_order_flow
```



最核心的数据库设计原则：

> **工单主表保存当前快照，业务子表保存具体业务过程，工单流转表保存生命周期历史，操作日志保存系统级审计。**

# 登录用户上下文与安全响应

`LoginUser` 保存用户编号、用户名、真实姓名和角色类型。角色固定为学生、维修人员、管理员三类。

阶段 1 已接入 `sys_user + BCrypt + JWT`。登录接口为 `POST /api/auth/login`，JWT 使用 `Authorization: Bearer <token>` 携带；服务端在每次认证时重新检查账号状态，停用或删除账号不能继续使用已签发令牌。

业务代码通过 `UserContext` 实时读取 `SecurityContextHolder`。只有 Authentication 已认证且 principal 为 `LoginUser` 时才允许读取，否则抛出错误码 10002。不得缓存当前用户，也不得将前端传入的用户编号作为操作人身份。

未认证请求返回 HTTP 401、错误码 10002；已认证但无权限返回 HTTP 403、错误码 10003。两类响应均为 UTF-8 JSON 的统一 `Result`，不得返回默认 HTML 或暴露认证异常详情。

角色专属接口严格隔离，通过 `@PreAuthorize` 显式声明。数据范围不使用 SQL AOP：列表查询由 Mapper 显式接收后端写入的身份条件，详情和修改由 Service 检查资源归属。管理员默认全量；维修人员仅本人及本人负责数据；学生仅本人提交数据。

阶段 2 的公开注册接口只允许创建学生账号，角色由服务端固定，客户端不能指定管理员或维修人员角色。管理员基础配置接口统一使用 `hasRole('ADMIN')`；启用故障类型和有效位置树属于业务选择数据，允许任意已登录角色读取。工作时间的 `createBy` 等操作人字段只从 `UserContext` 获取。

阶段 3 已将数据范围落实到工单查询。学生列表强制使用 `repair_order.student_uid = UserContext.getCurrentUserId()`；维修人员先用当前 `sys_user.id` 查询 `repair_worker.id`，再强制使用 `repair_order.current_assignee_id = 当前维修人员ID`；管理员不追加归属条件。详情先查询工单主记录并执行相同归属校验，通过后才读取过程、材料、返工、评价和流转数据。客户端提交的身份字段不能扩大查询范围。
# PLAN-4 学生报修安全边界

- 两个报修 POST 接口只允许 `STUDENT` 角色访问。
- `student_uid` 只取自 `UserContext`，请求体不接收该字段。
- `duplicate_flag` 由服务端 24 小时疑似重复结果决定，前端不能指定。
- Redis Key 统一由 `RedisConstant.repairOrderCreateKey(studentUid,bizNo)` 生成，TTL 为 10 分钟。
- Redis 只负责并发快速拦截；MySQL `(biz_type,user_id,biz_no)` 唯一约束负责最终幂等。
- 同一 bizNo 对应不同 `request_hash` 时返回 HTTP 409 / 17004，正在处理返回 HTTP 409 / 17003。

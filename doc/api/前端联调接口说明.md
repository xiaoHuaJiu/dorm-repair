# 前端联调接口说明

## 1. 通用约定

### 1.1 基础路径与协议

- 后端直连地址：`http://localhost:8811`。
- Nginx 统一入口：`http://localhost:8080`。
- 所有业务接口路径以 `/api` 开头，使用 JSON 和 UTF-8。
- 时间使用 ISO 8601 完整时间，例如 `2026-09-23T08:30:00`。

### 1.2 鉴权机制

除健康检查、登录和学生注册外，接口必须携带：

```http
Authorization: Bearer <JWT>
```

管理员、维修人员、学生只能访问各自角色入口。匿名访问返回 HTTP 401；角色不符或无权查看某张工单返回 HTTP 403。

### 1.3 统一响应结构

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

分页数据：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "total": 1,
    "pageNum": 1,
    "pageSize": 10,
    "records": []
  }
}
```

### 1.4 HTTP 状态与业务错误码

| HTTP | 业务码 | 含义 |
|---|---:|---|
| 200 | 0 | 成功 |
| 400 | 10001 | 请求参数错误 |
| 401 | 10002 | 未登录或登录状态失效 |
| 403 | 10003 | 角色无权访问接口 |
| 403 | 17002 | 当前用户无权访问指定工单 |
| 404 | 17001 | 工单不存在 |
| 409 | 17003 | 同一报修请求正在处理中 |
| 409 | 17004 | 同一 bizNo 被用于不同报修内容 |
| 500 | 50000 | 系统异常 |

## 2. 接口概览

| 接口 | 方法 | 角色 | 用途 |
|---|---|---|---|
| `/api/admin/repair-orders` | GET | 管理员 | 全量工单分页与组合筛选 |
| `/api/worker/repair-orders` | GET | 维修人员 | 当前分配给本人的工单分页 |
| `/api/student/repair-orders` | GET | 学生 | 本人报修工单分页 |
| `/api/admin/repair-orders/{id}` | GET | 管理员 | 任意工单聚合详情 |
| `/api/worker/repair-orders/{id}` | GET | 维修人员 | 当前分配给本人的工单详情 |
| `/api/student/repair-orders/{id}` | GET | 学生 | 本人报修工单详情 |
| `/api/student/repair-orders/check-duplicate` | POST | 学生 | 预检查 24 小时疑似重复，不写数据 |
| `/api/student/repair-orders` | POST | 学生 | 幂等创建报修工单 |

PLAN-2 的注册、故障类型、位置、维修人员、技能、负责区域和工作时间接口见《基础配置接口》。

## 3. 管理员工单列表

### 3.1 接口设计

`GET /api/admin/repair-orders`。管理员可查询全部未逻辑删除工单，筛选条件默认使用 AND 组合，默认按 `reportTime DESC、orderId DESC` 排序。

### 3.2 请求参数

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| pageNum | Integer | 否 | 默认 1，最小 1 |
| pageSize | Integer | 否 | 默认 10，最大 100 |
| orderNo | String | 否 | 工单编号模糊查询 |
| statusList | Integer[] | 否 | 多状态查询，可重复传参 |
| faultTypeId | Long | 否 | 故障类型 |
| campusId/areaId/buildingId/roomId | Long | 否 | 四级位置筛选 |
| workerId | Long | 否 | 当前负责人的 `repair_worker.id` |
| reportStartTime/reportEndTime | LocalDateTime | 否 | 闭区间，开始不得晚于结束 |
| exceptionFlag | Boolean | 否 | `true` 仅查异常工单 |
| suspectedDuplicate | Boolean | 否 | `true` 仅查疑似重复 |
| acceptTimeout | Boolean | 否 | `true` 查询待接单且截止时间已过 |
| completeTimeout | Boolean | 否 | `true` 查询维修中/返工中且截止时间已过 |

### 3.3 响应数据

列表记录包含工单 ID/编号/状态、学生、故障类型、四级位置、完整位置文本、当前维修人员、报修时间、接单及完成截止时间、异常/重复标记和两个实时超时字段。

### 3.4 响应示例

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "total": 1,
    "pageNum": 1,
    "pageSize": 10,
    "records": [{
      "orderId": 101,
      "orderNo": "RO202609230001",
      "status": 1,
      "statusName": "待接单",
      "faultTypeName": "水电",
      "roomName": "502室",
      "locationText": "东校区 / A区 / 1号楼 / 502室",
      "workerName": "维修人员甲",
      "acceptTimeout": false,
      "completeTimeout": false
    }]
  }
}
```

### 3.5 错误场景

- 未登录：HTTP 401 / 10002。
- 非管理员：HTTP 403 / 10003。
- 时间范围倒置或参数类型错误：HTTP 400 / 10001。

## 4. 维修人员工单列表

### 4.1 接口设计

`GET /api/worker/repair-orders`。服务端将当前 `sys_user.id` 转换为 `repair_worker.id`，强制查询 `current_assignee_id = 当前维修人员ID`。

### 4.2 请求参数

支持 `pageNum`、`pageSize`、`orderNo`、`statusList`、`faultTypeId`、四级位置、报修时间及超时筛选。即使客户端提交 `workerId`，该入口也会清除该参数，不能扩大范围。

### 4.3 响应数据与示例

响应分页结构与第 3 节一致，仅包含服务端强制范围内的工单。

### 4.4 错误场景

- 非维修人员角色：HTTP 403 / 10003。
- 当前账号没有维修人员档案：HTTP 404 / 15002。

## 5. 学生工单列表

### 5.1 接口设计

`GET /api/student/repair-orders`。服务端强制查询 `student_uid = 当前登录用户ID`，接口不接收 `studentUid`。

### 5.2 请求参数

支持 `pageNum`、`pageSize`、`statusList`、`faultTypeId`、四级位置和报修时间。客户端不能查询其他学生数据。

### 5.3 响应数据与错误场景

响应分页结构与第 3 节一致。非学生角色返回 HTTP 403 / 10003。

## 6. 工单聚合详情

### 6.1 接口设计

三个角色分别调用：

- `GET /api/admin/repair-orders/{id}`；
- `GET /api/worker/repair-orders/{id}`；
- `GET /api/student/repair-orders/{id}`。

底层复用同一个详情服务。服务端先查询工单并校验归属，再查询关联数据。

### 6.2 路径参数与上下文校验

`id` 为工单主键。管理员可查看任意工单；维修人员只能查看当前负责人为自己的工单；学生只能查看 `student_uid` 为自己的工单。

### 6.3 响应结构

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "baseInfo": {},
    "processRecords": [],
    "materialRecords": [],
    "reworkRecords": [],
    "evaluation": null,
    "flows": []
  }
}
```

- `baseInfo`：工单主信息、四级位置 ID、联系方式、故障描述、图片、负责人及各业务时间。该对象不返回逻辑删除、创建时间和更新时间等内部维护字段；`duplicateOrderId` 仅管理员响应可能出现，学生和维修人员响应中不返回该字段。
- `processRecords`：按 `recordTime、id` 升序。
- `materialRecords`：按 `useTime、id` 升序。
- `reworkRecords`：按 `reworkNo、id` 升序。
- `evaluation`：一个对象或 `null`。
- `flows`：按 `operationTime、id` 升序。

### 6.4 错误场景

- 工单不存在或已逻辑删除：HTTP 404 / 17001。
- 工单存在但不属于当前学生或维修人员：HTTP 403 / 17002。

## 7. 四级位置约定

`repair_area.area_type`：`1` 单位/校区、`2` 区域、`3` 楼栋、`4` 房间。合法关系只有根节点→单位/校区→区域→楼栋→房间。公共位置树和子节点接口会返回启用的第四级房间节点。

## 8. 学生报修与疑似重复检测

### 8.1 前端必须遵守的 bizNo 规则

- 用户进入一次新的报修流程时生成唯一 `bizNo`，建议使用 UUID，最大 64 个字符。
- 同一次报修的首次提交、网络超时重试和疑似重复确认必须保持同一个 `bizNo`。
- 第一次正式提交使用 `confirmDuplicate=false`；用户选择“仍然提交”时使用原 `bizNo` 并改为 `confirmDuplicate=true`。
- 只有报修明确成功、用户明确放弃，或者开始一笔全新报修时才能生成新 `bizNo`。
- 提交期间按钮必须进入 loading/禁用状态，防止连续点击；此措施不能替代服务端幂等。
- 网络超时后不得生成新 `bizNo`，应使用原请求内容和原 `bizNo` 重试。
- 前端不得提交 `studentUid`、`duplicateFlag`，也不得自行判断写入的重复标记。

### 8.2 疑似重复预检查

`POST /api/student/repair-orders/check-duplicate`

请求示例：

```json
{"campusId":1,"areaId":10,"buildingId":100,"roomId":1001,"faultTypeId":3}
```

服务端验证四级位置的存在、启用状态和父子关系，同时验证故障类型已启用。随后查询相同四级位置、相同故障类型、报修时间大于等于当前时间减 24 小时且状态为 0—5 的工单。该接口只用于改善交互，不写入任何业务数据。

响应示例：

```json
{"code":0,"message":"success","data":{"duplicate":true,"suspectedOrders":[{"orderId":10001,"orderNo":"RO202609240001","faultTypeName":"水电维修","locationText":"东校区 / A区 / 1号楼 / 502","reportTime":"2026-09-24T08:00:00","status":2,"statusName":"维修中"}]}}
```

疑似工单可能由其他学生提交，因此只返回上述判断所需字段，不返回联系方式、学生身份、维修人员内部信息或调度信息。

### 8.3 正式创建报修

`POST /api/student/repair-orders`

请求字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| bizNo | String | 是 | 本次业务提交唯一标识，同一次重试保持不变 |
| campusId/areaId/buildingId/roomId | Long | 是 | 四级位置完整链路 |
| faultTypeId | Long | 是 | 已启用的故障类型 |
| locationDetail | String | 否 | 最长 255 字符 |
| problemDescription | String | 是 | 最长 1000 字符 |
| contactName | String | 是 | 最长 100 字符 |
| contactPhone | String | 是 | 6—30 位数字及常见电话符号 |
| imageUrls | String[] | 否 | 已上传完成的附件引用，最多 9 个；本接口不上传文件 |
| confirmDuplicate | Boolean | 是 | 是否在发现疑似重复后继续创建 |

首次请求示例：

```json
{"bizNo":"8d4892f9-5f58-45a7-bd03-7cb8a670eb12","campusId":1,"areaId":10,"buildingId":100,"roomId":1001,"faultTypeId":3,"problemDescription":"宿舍灯不亮","contactName":"张三","contactPhone":"13800138000","imageUrls":[],"confirmDuplicate":false}
```

无重复时返回 `created=true、duplicate=false`。存在疑似重复且未确认时仍返回 HTTP 200：

```json
{"code":0,"message":"success","data":{"created":false,"duplicate":true,"orderId":null,"orderNo":null,"suspectedOrders":[]}}
```

用户确认后复用原 `bizNo` 并提交 `confirmDuplicate=true`；创建结果为 `created=true、duplicate=true`，数据库 `duplicate_flag=1`。成功创建会原子写入工单、首条业务流转、操作日志和 MySQL 幂等成功记录。创建事务提交后，服务端通过专用线程池异步执行自动派单，因此 HTTP 200 和 `created=true` 只表示工单创建成功，不表示响应返回时派单已经完成。前端应以工单详情中的最新 `status` 和负责人字段为准，不得根据创建响应自行展示“已派单”。

自动派单成功后，工单变为 `1-待接单`，写入当前维修人员、派单时间和按 30 分钟有效工作时间计算的接单截止时间。暂无匹配人员、暂无工作时间方案或异步执行异常时，工单保持 `0-待派单` 且负责人为空，服务端生成去重的管理员派单失败告警并由定时补偿任务重试；这些内部处理不改变本接口统一响应结构。

### 8.4 幂等响应和错误场景

- 相同学生、相同 `bizNo`、相同业务内容再次请求：HTTP 200，返回第一次创建结果，不创建第二张工单。
- 相同 `bizNo` 的 `confirmDuplicate=false → true` 是合法流程；请求摘要不包含该字段。
- 相同学生复用 `bizNo` 但修改位置、故障、描述、联系方式或附件：HTTP 409 / 17004。
- 同一请求仍在执行：HTTP 409 / 17003，前端应提示“报修正在提交中，请勿重复操作”，不得自动更换 `bizNo`。
- 位置不存在返回 HTTP 404 / 14002；位置停用返回 HTTP 400 / 14004；层级不合法返回 HTTP 400 / 14001。
- 故障类型不存在返回 HTTP 404 / 13002；故障类型停用返回 HTTP 400 / 13003。
- 匿名访问返回 HTTP 401；非学生角色返回 HTTP 403。

## 9. 维修人员主流程接口

### 9.1 通用约定

以下接口统一使用 `/api/worker/repair-orders/{id}` 前缀，只允许维修人员访问。服务端从登录上下文解析 `sys_user.id`，再映射为 `repair_worker.id`；前端不得传 `workerId`。每次操作都会再次校验当前维修人员是否为 `current_assignee_id`，不能只依赖列表页和按钮显隐。

状态变化接口使用数据库条件更新和事务保护。重复点击、页面状态过期或并发操作导致状态已变化时返回 HTTP 409 / 10005；操作他人工单返回 HTTP 403 / 17002；工单不存在返回 HTTP 404 / 17001。前端提交按钮必须在请求期间进入 loading 和禁用状态，收到响应后重新拉取工单详情，但按钮防重复不能替代服务端校验。

图片字段只接收已经上传完成的 MinIO 对象引用或可访问地址。本阶段尚未提供文件上传接口，前端不能把二进制文件或 Base64 内容直接提交到这些字段。

### 9.2 接单

`POST /api/worker/repair-orders/{id}/accept`

请求体可为空，也可传预计完成时间：

```json
{"expectedCompleteTime":"2026-09-25T18:00:00"}
```

仅 `1-待接单` 且未超过 `acceptDeadline` 的当前负责人可操作。预计完成时间必须晚于接单时间；未填写时 `completeDeadline=acceptTime+24小时`，填写时二者相同。成功后状态为 `2-维修中`。

### 9.3 添加维修过程

`POST /api/worker/repair-orders/{id}/process-records`

```json
{"content":"已完成线路检查","imageUrls":["repair/2026/process-1.jpg"]}
```

`content` 必填且最多 1000 字符，`imageUrls` 最多 9 个。仅 `2-维修中`、`4-返工中` 可添加；该操作不改变工单状态。

### 9.4 登记材料

`POST /api/worker/repair-orders/{id}/materials`

```json
{"materialName":"LED灯泡","specification":"20W","quantity":1.00,"unit":"个","remark":"更换损坏灯泡"}
```

材料名称、数量和单位必填，数量最小 `0.01` 且最多两位小数。仅 `2-维修中`、`4-返工中` 可添加。材料属于内部维修记录，学生工单详情中的 `materialRecords` 固定返回空数组；管理员和当前负责人可查看。

### 9.5 中断维修

`POST /api/worker/repair-orders/{id}/interrupt`

```json
{"interruptReasonType":1,"content":"等待备用材料"}
```

第一期只允许 `2-维修中 → 5-已中断`。原因枚举：`1-等待材料`、`2-第三方介入`、`3-现场条件限制`、`4-其他`。成功后同时写入中断过程、工单流转和操作日志。

### 9.6 恢复维修

`POST /api/worker/repair-orders/{id}/resume`

请求体可为空：

```json
{"remark":"材料到位，恢复维修"}
```

只允许 `5-已中断 → 2-维修中`。未填写说明时服务端记录“恢复维修”。

### 9.7 提交维修结果

`POST /api/worker/repair-orders/{id}/submit-result`

```json
{"resultDescription":"维修完成并通过通电测试","resultImageUrls":["repair/2026/result-1.jpg"]}
```

仅 `2-维修中`、`4-返工中` 可提交。成功后状态变为 `3-待确认` 并写入 `repairSubmitTime`，不会提前写 `completeTime`，负责人仍保留。已中断工单必须先恢复，待确认工单不能重复提交。

### 9.8 统一成功响应

上述六个接口成功响应均为：

```json
{"code":0,"message":"success","data":null}
```

接单、中断、恢复和提交结果会写工单流转；六种操作都会写系统操作日志。前端操作成功后继续复用 `GET /api/worker/repair-orders/{id}` 获取最新状态、过程时间线和材料记录。

# 前端联调接口说明

## 1. 通用约定

### 1.1 基础路径与协议

- 后端直连地址：`http://localhost:8811`。
- Nginx 统一入口：`http://localhost:8080`。
- 所有业务接口路径以 `/api` 开头，使用 JSON 和 UTF-8。
- 时间使用 ISO 8601 完整时间，例如 `2026-09-23T08:30:00`。

### 1.2 鉴权机制

除健康检查、登录和学生注册外，接口必须携带：

```http
Authorization: Bearer <JWT>
```

管理员、维修人员、学生只能访问各自角色入口。匿名访问返回 HTTP 401；角色不符或无权查看某张工单返回 HTTP 403。

### 1.3 统一响应结构

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

分页数据：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "total": 1,
    "pageNum": 1,
    "pageSize": 10,
    "records": []
  }
}
```

### 1.4 HTTP 状态与业务错误码

| HTTP | 业务码 | 含义 |
|---|---:|---|
| 200 | 0 | 成功 |
| 400 | 10001 | 请求参数错误 |
| 401 | 10002 | 未登录或登录状态失效 |
| 403 | 10003 | 角色无权访问接口 |
| 403 | 17002 | 当前用户无权访问指定工单 |
| 404 | 17001 | 工单不存在 |
| 409 | 17003 | 同一报修请求正在处理中 |
| 409 | 17004 | 同一 bizNo 被用于不同报修内容 |
| 400 | 18001/18002/18003/18004 | 文件为空、业务类型错误、格式不允许或文件过大 |
| 403 | 18006 | 不是文件上传人，无权绑定或删除 |
| 404 | 18005 | 文件不存在或不可用 |
| 409 | 18007 | 文件已经绑定业务 |
| 500 | 18008/18009 | 文件上传或删除失败 |
| 500 | 50000 | 系统异常 |

## 2. 登录与学生注册

### 2.1 登录

`POST /api/auth/login`。匿名可访问。

请求字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| username | String | 是 | 登录账号 |
| password | String | 是 | 登录密码 |

成功响应：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "token": "<JWT>",
    "user": { "userId": 1, "username": "student1", "realName": "林同学", "roleType": 1 }
  }
}
```

- `token`：JWT，后续请求使用 `Authorization: Bearer <token>` 携带。
- `user.roleType`：`1` 学生、`2` 维修人员、`3` 管理员，与后端 `UserRoleEnum` 一致。
- 前端登录成功后保存令牌与用户信息，并按 `roleType` 跳转对应端首页；收到未知角色值时不进入任何业务端。

错误场景：

- 参数缺失：HTTP 400 / 10001。
- 账号或密码错误、账号已停用：HTTP 401 / 10002，前端在登录表单内展示后端返回的错误文案。

### 2.2 学生注册

`POST /api/auth/register`。匿名可访问，只允许创建学生账号。

请求字段：

| 字段 | 类型 | 必填 | 校验 |
|---|---|---|---|
| username | String | 是 | 最长 100 字符 |
| password | String | 是 | 8—64 字符 |
| confirmPassword | String | 是 | 必须与 password 一致 |
| realName | String | 是 | 最长 100 字符 |
| phone | String | 否 | 空或 `1[3-9]\d{9}` 手机号格式 |

- 服务端固定创建 `STUDENT` 角色账号，忽略客户端额外提交的角色字段。
- 注册成功不自动签发令牌；前端清空密码字段并切回登录表单，不保留注册密码。
- 用户名冲突等业务错误以统一 `Result` 返回，前端在注册表单内展示。

## 4. 管理员工单列表

### 4.1 接口设计

`GET /api/admin/repair-orders`。管理员可查询全部未逻辑删除工单，筛选条件默认使用 AND 组合，默认按 `reportTime DESC、orderId DESC` 排序。

### 4.2 请求参数

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| pageNum | Integer | 否 | 默认 1，最小 1 |
| pageSize | Integer | 否 | 默认 10，最大 100 |
| orderNo | String | 否 | 工单编号模糊查询 |
| statusList | Integer[] | 否 | 多状态查询，可重复传参（`statusList=0&statusList=1`）。前端 axios 已配置 `paramsSerializer: { indexes: null }` 以重复参数形态序列化；空方括号形态（`statusList[]=0`）Spring 无法绑定，禁止使用 |
| faultTypeId | Long | 否 | 故障类型 |
| campusId/areaId/buildingId/roomId | Long | 否 | 四级位置筛选 |
| workerId | Long | 否 | 当前负责人的 `repair_worker.id` |
| reportStartTime/reportEndTime | LocalDateTime | 否 | 闭区间，开始不得晚于结束 |
| exceptionFlag | Boolean | 否 | `true` 仅查异常工单 |
| suspectedDuplicate | Boolean | 否 | `true` 仅查疑似重复 |
| acceptTimeout | Boolean | 否 | `true` 查询待接单且截止时间已过 |
| completeTimeout | Boolean | 否 | `true` 查询维修中/返工中且截止时间已过 |

### 4.3 响应数据

列表记录包含工单 ID/编号/状态、学生、故障类型、四级位置、完整位置文本、当前维修人员、报修时间、接单及完成截止时间、异常/重复标记和两个实时超时字段。

### 4.4 响应示例

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "total": 1,
    "pageNum": 1,
    "pageSize": 10,
    "records": [{
      "orderId": 101,
      "orderNo": "RO202609230001",
      "status": 1,
      "statusName": "待接单",
      "faultTypeName": "水电",
      "roomName": "502室",
      "locationText": "东校区 / A区 / 1号楼 / 502室",
      "workerName": "维修人员甲",
      "acceptTimeout": false,
      "completeTimeout": false
    }]
  }
}
```

### 4.5 错误场景

- 未登录：HTTP 401 / 10002。
- 非管理员：HTTP 403 / 10003。
- 时间范围倒置或参数类型错误：HTTP 400 / 10001。

## 5. 维修人员工单列表

### 5.1 接口设计

`GET /api/worker/repair-orders`。服务端将当前 `sys_user.id` 转换为 `repair_worker.id`，强制查询 `current_assignee_id = 当前维修人员ID`。

### 5.3 响应数据与示例

响应分页结构与第 4 节一致，仅包含服务端强制范围内的工单。

### 5.4 错误场景

- 非维修人员角色：HTTP 403 / 10003。
- 当前账号没有维修人员档案：HTTP 404 / 15002。

### 6.2 请求参数

## 7. 工单聚合详情

### 7.1 接口设计

三个角色分别调用：

- `GET /api/admin/repair-orders/{id}`；
- `GET /api/worker/repair-orders/{id}`；
- `GET /api/student/repair-orders/{id}`。

底层复用同一个详情服务。服务端先查询工单并校验归属，再查询关联数据。

### 7.2 路径参数与上下文校验

`id` 为工单主键。管理员可查看任意工单；维修人员只能查看当前负责人为自己的工单；学生只能查看 `student_uid` 为自己的工单。

### 7.3 响应结构

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "baseInfo": {},
    "processRecords": [],
    "materialRecords": [],
    "reworkRecords": [],
    "evaluation": null,
    "flows": []
  }
}
```

- `baseInfo`：工单主信息、四级位置 ID、联系方式、故障描述、图片、负责人及各业务时间。该对象不返回逻辑删除、创建时间和更新时间等内部维护字段；`duplicateOrderId` 仅管理员响应可能出现，学生和维修人员响应中不返回该字段。
- `processRecords`：按 `recordTime、id` 升序。
- `materialRecords`：按 `useTime、id` 升序。
- `reworkRecords`：按 `reworkNo、id` 升序。
- `evaluation`：一个对象或 `null`。
- `flows`：按 `operationTime、id` 升序。

### 7.4 错误场景

- 工单不存在或已逻辑删除：HTTP 404 / 17001。
- 工单存在但不属于当前学生或维修人员：HTTP 403 / 17002。

## 8. 四级位置约定

`repair_area.area_type`：`1` 单位/校区、`2` 区域、`3` 楼栋、`4` 房间。合法关系只有根节点→单位/校区→区域→楼栋→房间。公共位置树和子节点接口会返回启用的第四级房间节点。

## 9. 学生报修与疑似重复检测

### 9.1 前端必须遵守的 bizNo 规则

- 用户进入一次新的报修流程时生成唯一 `bizNo`，建议使用 UUID，最大 64 个字符。
- 同一次报修的首次提交、网络超时重试和疑似重复确认必须保持同一个 `bizNo`。
- 第一次正式提交使用 `confirmDuplicate=false`；用户选择“仍然提交”时使用原 `bizNo` 并改为 `confirmDuplicate=true`。
- 只有报修明确成功、用户明确放弃，或者开始一笔全新报修时才能生成新 `bizNo`。
- 提交期间按钮必须进入 loading/禁用状态，防止连续点击；此措施不能替代服务端幂等。
- 网络超时后不得生成新 `bizNo`，应使用原请求内容和原 `bizNo` 重试。
- 前端不得提交 `studentUid`、`duplicateFlag`，也不得自行判断写入的重复标记。

### 9.2 疑似重复预检查

`POST /api/student/repair-orders/check-duplicate`

请求示例：

```json
{"campusId":1,"areaId":10,"buildingId":100,"roomId":1001,"faultTypeId":3}
```

服务端验证四级位置的存在、启用状态和父子关系，同时验证故障类型已启用。随后查询相同四级位置、相同故障类型、报修时间大于等于当前时间减 24 小时且状态为 0—5 的工单。该接口只用于改善交互，不写入任何业务数据。

响应示例：

```json
{"code":0,"message":"success","data":{"duplicate":true,"suspectedOrders":[{"orderId":10001,"orderNo":"RO202609240001","faultTypeName":"水电维修","locationText":"东校区 / A区 / 1号楼 / 502","reportTime":"2026-09-24T08:00:00","status":2,"statusName":"维修中"}]}}
```

疑似工单可能由其他学生提交，因此只返回上述判断所需字段，不返回联系方式、学生身份、维修人员内部信息或调度信息。

### 9.3 正式创建报修

`POST /api/student/repair-orders`

请求字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| bizNo | String | 是 | 本次业务提交唯一标识，同一次重试保持不变 |
| campusId/areaId/buildingId/roomId | Long | 是 | 四级位置完整链路 |
| faultTypeId | Long | 是 | 已启用的故障类型 |
| locationDetail | String | 否 | 最长 255 字符 |
| problemDescription | String | 是 | 最长 1000 字符 |
| contactName | String | 是 | 最长 100 字符 |
| contactPhone | String | 是 | 6—30 位数字及常见电话符号 |
| fileIds | Long[] | 否 | 公共上传接口返回的文件 ID，去重后最多 9 个；本接口不上传文件 |
| confirmDuplicate | Boolean | 是 | 是否在发现疑似重复后继续创建 |

首次请求示例：

```json
{"bizNo":"8d4892f9-5f58-45a7-bd03-7cb8a670eb12","campusId":1,"areaId":10,"buildingId":100,"roomId":1001,"faultTypeId":3,"problemDescription":"宿舍灯不亮","contactName":"张三","contactPhone":"13800138000","fileIds":[],"confirmDuplicate":false}
```

无重复时返回 `created=true、duplicate=false`。存在疑似重复且未确认时仍返回 HTTP 200：

```json
{"code":0,"message":"success","data":{"created":false,"duplicate":true,"orderId":null,"orderNo":null,"suspectedOrders":[]}}
```

用户确认后复用原 `bizNo` 并提交 `confirmDuplicate=true`；创建结果为 `created=true、duplicate=true`，数据库 `duplicate_flag=1`。成功创建会原子写入工单、首条业务流转、操作日志和 MySQL 幂等成功记录。创建事务提交后，服务端通过专用线程池异步执行自动派单，因此 HTTP 200 和 `created=true` 只表示工单创建成功，不表示响应返回时派单已经完成。前端应以工单详情中的最新 `status` 和负责人字段为准，不得根据创建响应自行展示“已派单”。

自动派单成功后，工单变为 `1-待接单`，写入当前维修人员、派单时间和按 30 分钟有效工作时间计算的接单截止时间。暂无匹配人员、暂无工作时间方案或异步执行异常时，工单保持 `0-待派单` 且负责人为空，服务端生成去重的管理员派单失败告警并由定时补偿任务重试；这些内部处理不改变本接口统一响应结构。

### 9.4 幂等响应和错误场景

- 相同学生、相同 `bizNo`、相同业务内容再次请求：HTTP 200，返回第一次创建结果，不创建第二张工单。
- 相同 `bizNo` 的 `confirmDuplicate=false → true` 是合法流程；请求摘要不包含该字段。
- 相同学生复用 `bizNo` 但修改位置、故障、描述、联系方式或附件：HTTP 409 / 17004。
- 同一请求仍在执行：HTTP 409 / 17003，前端应提示“报修正在提交中，请勿重复操作”，不得自动更换 `bizNo`。
- 位置不存在返回 HTTP 404 / 14002；位置停用返回 HTTP 400 / 14004；层级不合法返回 HTTP 400 / 14001。
- 故障类型不存在返回 HTTP 404 / 13002；故障类型停用返回 HTTP 400 / 13003。
- 匿名访问返回 HTTP 401；非学生角色返回 HTTP 403。

## 10. 维修人员主流程接口

### 10.1 通用约定

以下接口统一使用 `/api/worker/repair-orders/{id}` 前缀，只允许维修人员访问。服务端从登录上下文解析 `sys_user.id`，再映射为 `repair_worker.id`；前端不得传 `workerId`。每次操作都会再次校验当前维修人员是否为 `current_assignee_id`，不能只依赖列表页和按钮显隐。

状态变化接口使用数据库条件更新和事务保护。重复点击、页面状态过期或并发操作导致状态已变化时返回 HTTP 409 / 10005；操作他人工单返回 HTTP 403 / 17002；工单不存在返回 HTTP 404 / 17001。前端提交按钮必须在请求期间进入 loading 和禁用状态，收到响应后重新拉取工单详情，但按钮防重复不能替代服务端校验。

图片字段只接收已经上传完成的 MinIO 对象引用（第 11 节公共上传接口返回的 `fileId`）。前端不能把二进制文件或 Base64 内容直接提交到这些字段。

### 10.2 接单

`POST /api/worker/repair-orders/{id}/accept`

请求体可为空，也可传预计完成时间：

```json
{"expectedCompleteTime":"2026-09-25T18:00:00"}
```

仅 `1-待接单` 且未超过 `acceptDeadline` 的当前负责人可操作。预计完成时间必须晚于接单时间；未填写时 `completeDeadline=acceptTime+24小时`，填写时二者相同。成功后状态为 `2-维修中`。

### 10.3 添加维修过程

`POST /api/worker/repair-orders/{id}/process-records`

```json
{"content":"已完成线路检查","fileIds":[10002]}
```

`content` 必填且最多 1000 字符，`fileIds` 去重后最多 9 个，且必须来自当前维修人员以 `PROCESS` 类型上传的未绑定文件。仅 `2-维修中`、`4-返工中` 可添加；该操作不改变工单状态。

### 10.4 登记材料

`POST /api/worker/repair-orders/{id}/materials`

```json
{"materialName":"LED灯泡","specification":"20W","quantity":1.00,"unit":"个","remark":"更换损坏灯泡"}
```

材料名称、数量和单位必填，数量最小 `0.01` 且最多两位小数。仅 `2-维修中`、`4-返工中` 可添加。材料属于内部维修记录，学生工单详情中的 `materialRecords` 固定返回空数组；管理员和当前负责人可查看。

### 10.5 中断维修

`POST /api/worker/repair-orders/{id}/interrupt`

```json
{"interruptReasonType":1,"content":"等待备用材料"}
```

第一期只允许 `2-维修中 → 5-已中断`。原因枚举：`1-等待材料`、`2-第三方介入`、`3-现场条件限制`、`4-其他`。成功后同时写入中断过程、工单流转和操作日志。

### 10.6 恢复维修

`POST /api/worker/repair-orders/{id}/resume`

请求体可为空：

```json
{"remark":"材料到位，恢复维修"}
```

只允许 `5-已中断 → 2-维修中`。未填写说明时服务端记录“恢复维修”。

### 10.7 提交维修结果

`POST /api/worker/repair-orders/{id}/submit-result`

```json
{"resultDescription":"维修完成并通过通电测试","fileIds":[10003]}
```

仅 `2-维修中`、`4-返工中` 可提交。成功后状态变为 `3-待确认` 并写入 `repairSubmitTime`，不会提前写 `completeTime`，负责人仍保留。已中断工单必须先恢复，待确认工单不能重复提交。

### 10.8 统一成功响应

上述六个接口成功响应均为：

```json
{"code":0,"message":"success","data":null}
```

接单、中断、恢复和提交结果会写工单流转；六种操作都会写系统操作日志。前端操作成功后继续复用 `GET /api/worker/repair-orders/{id}` 获取最新状态、过程时间线和材料记录。

## 10. PLAN-7 学生确认、评价与返工

新增 `POST /api/student/repair-orders/{id}/confirm`、`POST /api/student/repair-orders/{id}/evaluation`、`POST /api/student/repair-orders/{id}/rework`。完整契约见《学生确认评价与返工接口.md》。

前端已接入：`api/order.ts` 新增 `confirmRepairOrder/submitRepairEvaluation/submitRepairRework` 三个函数，学生验收页（`/student/orders/:id/review`）确认/评价/返工按钮已启用，返工弹窗支持原因 + REWORK 图片上传。

身份完全取自登录上下文，不接收 `studentUid` 或 `workerId`。前端请求期间必须保持按钮 loading 和禁用，成功或 409 后重新拉取详情。评价只能提交一次；返工请求使用 `fileIds`，文件须先通过公共上传接口以 `REWORK` 类型上传。

## 11. 公共文件上传与业务附件

前端已接入：`api/file.ts` 提供 `uploadFile(file, bizType)` 与 `deleteFile(fileId)`；`ImageUploader` 组件改为管理 `{fileId, previewUrl}` 文件列表（选择后由页面层上传，移除时删除未绑定文件）；报修弹窗、维修过程、完成维修、学生返工弹窗四处入口已启用；三个工单详情页通过 `FileGallery` 展示 `baseInfo.files`、`processRecords[].files`、`reworkRecords[].files`。

### 11.1 通用流程

前端先逐个调用公共上传接口，保存响应中的 `fileId`；用户最终提交报修、维修过程、维修结果或返工时只传 `fileIds`。业务接口与附件关系在同一数据库事务中写入，绑定失败时业务记录一并回滚。固定 MinIO 地址不得保存到业务表，详情接口返回动态生成的临时 `previewUrl`。

前端必须执行以下交互约束：上传和最终提交期间保持按钮禁用，防止重复点击；上传成功但业务提交失败时保留 `fileId` 以便重试；移除尚未提交的附件时调用删除接口；图片和视频均按 `fileType` 决定预览组件，不按 URL 后缀判断。

### 11.2 上传文件

`POST /api/files/upload`，请求类型为 `multipart/form-data`，必须携带 JWT。

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| file | File | 是 | 图片或视频二进制 |
| bizType | String | 是 | `REPAIR`、`PROCESS` 或 `REWORK` |

权限规则：学生只能上传 `REPAIR`、`REWORK`；维修人员只能上传 `PROCESS`；管理员当前不能使用上传接口。图片支持 JPG/JPEG/PNG/WebP，单文件不超过 10MB；视频支持 MP4/MOV/WebM，单文件不超过 200MB。后缀与 MIME 必须同时匹配。

成功响应示例：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "fileId": 10001,
    "originalName": "宿舍漏水.jpg",
    "fileType": "IMAGE",
    "contentType": "image/jpeg",
    "fileSize": 1837421,
    "objectName": "repair/2026/09/24/6c65d889d58f4e50a8437fcb61f70a25.jpg",
    "previewUrl": "MinIO 临时签名地址"
  }
}
```

`previewUrl` 默认有效期 30 分钟，只用于当前预览；刷新工单详情后会获得新地址。前端持久状态只保存 `fileId`。

### 11.3 删除未绑定文件

`DELETE /api/files/{fileId}`。仅上传人本人可删除，且文件不能已经关联报修、维修过程或返工记录。成功返回统一空响应；已绑定返回 HTTP 409/业务码 `18007`，他人文件返回 HTTP 403/业务码 `18006`。

### 11.4 业务请求字段

以下接口的旧 URL 数组字段不再使用：

| 业务接口 | 文件用途 | 请求字段 |
|---|---|---|
| `POST /api/student/repair-orders` | 报修附件 | `fileIds: Long[]`，文件 `bizType=REPAIR` |
| `POST /api/worker/repair-orders/{id}/process-records` | 维修过程附件 | `fileIds: Long[]`，文件 `bizType=PROCESS` |
| `POST /api/worker/repair-orders/{id}/submit-result` | 维修结果附件 | `fileIds: Long[]`，文件 `bizType=PROCESS` |
| `POST /api/student/repair-orders/{id}/rework` | 返工附件 | `fileIds: Long[]`，文件 `bizType=REWORK` |

每次提交会去重，去重后最多 9 个；文件必须上传成功、未删除、未绑定、属于当前操作者且用途一致。一个 `fileId` 不允许跨业务复用。

### 11.5 详情响应

三类角色的工单详情保持原有数据权限。`baseInfo.files` 返回报修附件；每条 `processRecords[].files` 返回该过程或维修结果附件；每条 `reworkRecords[].files` 返回返工附件。文件对象结构如下：

```json
{
  "fileId": 10001,
  "originalName": "宿舍漏水.jpg",
  "fileType": "IMAGE",
  "contentType": "image/jpeg",
  "fileSize": 1837421,
  "previewUrl": "MinIO 临时签名地址"
}
```

### 11.6 错误场景

- 空文件、非法 `bizType`、后缀/MIME 不匹配或超限分别返回明确的 18xxx 业务码。
- MinIO 上传失败时不写文件元数据；MinIO 成功而数据库写入失败时，后端尝试删除已上传对象进行补偿。
- 未绑定文件可由用户主动删除；超过 24 小时的未绑定文件由定时任务分批清理，单条失败不会中断其他文件。

## 12. PLAN-8 维修转派

### 12.1 通用约定与前端交互

转派申请和转派审批都是关键写操作。前端必须在页面首次打开时生成一个不超过 64 字符的 `bizNo`，同一次操作因超时或网络失败而重试时复用原值；用户明确重新发起另一项操作时才生成新值。提交期间按钮必须保持 loading 和禁用，防止重复点击。按钮防重不能替代服务端幂等。

维修人员提交申请后，工单状态和当前负责人保持不变，页面只能提示“转派申请已提交，等待管理员审批”，不得提前显示已转派。管理员审批前应重新查询详情确认 `approvalStatus=0`；审批成功或 HTTP 409 后重新拉取转派详情和工单详情。

枚举约定：

- `reasonType`：`OUT_OF_SCOPE`、`NO_SKILL`、`UNAVAILABLE`、`NEED_OTHER_TRADE`、`OVERLOAD`、`OTHER`。
- `approvalStatus`：`0-待审批`、`1-已通过`、`2-已驳回`、`3-已失效`。
- `executeStatus`：`0-未执行`、`1-执行中`、`2-执行成功`、`3-执行失败`。
- `action`：`APPROVE` 或 `REJECT`。

### 12.2 维修人员发起转派申请

`POST /api/worker/repair-orders/{orderId}/transfer-requests`

```json
{
  "bizNo": "transfer-20260924-0001",
  "reasonType": "NO_SKILL",
  "reason": "需要其他专业人员处理"
}
```

`reasonType=OTHER` 时 `reason` 必填，其他原因下可不填；说明最多 500 字。只有工单当前负责人可以申请，且工单必须处于待接单、维修中、返工中或已中断状态。同一工单已有待审批申请时，使用不同 `bizNo` 再次提交返回 HTTP 409；相同 `bizNo`、相同内容重试返回第一次结果且 `replayed=true`。

```json
{"code":0,"message":"success","data":{"requestId":8001,"replayed":false}}
```

### 12.3 维修人员查询本人申请

`GET /api/worker/transfer-requests`，支持 `pageNum`、`pageSize`、`orderNo`、`approvalStatus`、`createStartTime`、`createEndTime`。服务端强制按当前登录维修人员过滤，不接收前端传入的 `applicantWorkerId`。

`GET /api/worker/transfer-requests/{id}` 只允许查看本人申请；他人申请返回 HTTP 403。

### 12.4 管理员查询转派申请

`GET /api/admin/transfer-requests`，支持 `pageNum`、`pageSize`、`orderNo`、`applicantWorkerId`、`approvalStatus`、`createStartTime`、`createEndTime`。

`GET /api/admin/transfer-requests/{id}` 返回转派申请、审批执行结果以及关联工单的编号、状态和当前负责人。列表和详情中的主要字段如下：

```json
{
  "id": 8001,
  "orderId": 10001,
  "orderNo": "RO202609240001",
  "applicantWorkerId": 101,
  "originalAssigneeId": 101,
  "reasonType": 2,
  "reasonDescription": "需要其他专业人员处理",
  "approvalStatus": 0,
  "reviewAdminId": null,
  "reviewRemark": null,
  "reviewTime": null,
  "executeStatus": 0,
  "newAssigneeId": null,
  "executeTime": null,
  "failureReason": null,
  "createTime": "2026-09-24T19:00:00",
  "orderStatus": 2,
  "currentAssigneeId": 101
}
```

### 12.5 管理员审批

`POST /api/admin/transfer-requests/{id}/review`

```json
{"bizNo":"transfer-review-20260924-0001","action":"APPROVE","remark":"同意转派"}
```

相同管理员、相同 `bizNo`、相同审批内容重试时返回首次结果且不重复派单。复用 `bizNo` 但改变申请编号、审批动作或意见返回 HTTP 409 / 19006。只有待审批记录可以处理；已处理记录返回 HTTP 409 / 19003。审批时若负责人或工单状态已经变化，返回 HTTP 409 / 19004，不执行旧申请。

驳回只更新审批记录，原负责人和工单状态不变。通过后服务端调用统一自动派单并强制排除原负责人。成功示例：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "requestId": 8001,
    "reviewSuccess": true,
    "dispatchSuccess": true,
    "newAssigneeId": 102,
    "failureReason": null,
    "replayed": false
  }
}
```

自动派单失败不表示审批失败，接口仍返回 HTTP 200、`reviewSuccess=true`、`dispatchSuccess=false`，并返回 `failureReason`。此时工单进入待派单、当前负责人为空，服务端生成管理员异常提醒；前端应提示“审批已通过，但未找到可用维修人员，已进入人工派单处理”，不能提示“审批失败”。

### 12.6 错误场景

- 未登录返回 HTTP 401，角色不匹配或维修人员访问他人申请返回 HTTP 403。
- 工单不存在返回 HTTP 404 / 17001；转派申请不存在返回 HTTP 404 / 19005。
- 当前状态不允许申请返回 HTTP 409 / 19001；已有待审批申请返回 HTTP 409 / 19002。
- 申请已处理返回 HTTP 409 / 19003；审批时工单已变化返回 HTTP 409 / 19004。
- `bizNo` 被不同内容复用返回 HTTP 409 / 19006；同一请求仍处理中返回 HTTP 409 / 17003。

## 13. 维修人员请假与管理员审批（PLAN-9）

> 本章接口与后端实现已完成开发，**暂未测试**（项目当前无法启动）。完整契约见《维修人员请假接口.md》。

### 13.1 状态枚举约定

- `approvalStatus`（审批状态）：`0 待审批`、`1 已通过`、`2 已驳回`。
- `reassignStatus`（转派处理状态）：`0 未处理`、`1 处理中`、`2 已完成`、`3 部分失败`。
- 审批通过只代表管理员同意，不代表请假已经开始；请假生效由后台定时任务在开始时间到达后执行。
- `workStatus`（维修人员工作状态）：`0 正常`、`1 请假中`、`2 停用`。请假生效后置为 `1`，结束后恢复 `0`。

### 13.2 提交请假申请

`POST /api/worker/leave-requests`。只允许维修人员。

请求字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| bizNo | String | 是 | 本次提交唯一标识，同一次重试保持不变，最长 64 字符 |
| startTime | LocalDateTime | 是 | 请假开始时间，必须早于 endTime |
| endTime | LocalDateTime | 是 | 请假结束时间，必须晚于当前时间 |
| reason | String | 是 | 请假事由，最长 500 字符 |

服务端从登录上下文解析维修人员，前端不得传 `workerId`。创建成功返回 `{ "leaveId": 10001, "approvalStatus": 0 }`。

幂等规则：相同人员、相同 `bizNo`、相同内容重试返回首次结果；相同 `bizNo` 不同内容返回 HTTP 409 / 17004；同一请求仍在执行返回 HTTP 409 / 17003。时间重叠校验只针对待审批和已通过的请假（`start_time < 新endTime AND end_time > 新startTime`），重叠时返回 HTTP 409 / 10005。

### 13.3 查询请假

- `GET /api/worker/leave-requests`：本人请假分页，可选 `approvalStatus` 筛选；强制限定当前维修人员。
- `GET /api/worker/leave-requests/{id}`：本人请假详情，非本人记录返回 HTTP 404 / 10004。
- `GET /api/admin/leave-requests`：全量分页，可选 `workerId`、`approvalStatus`、`startTime`、`endTime` 筛选。
- `GET /api/admin/leave-requests/{id}`：任意请假详情。

列表与详情均返回 `approvalStatusName`、`reassignStatusName` 中文名称；详情额外包含 `reviewAdminName`、`reviewRemark`、`reviewTime`。

### 13.4 审批请假

`POST /api/admin/leave-requests/{id}/review`。只允许管理员。

请求字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| bizNo | String | 是 | 本次审批提交唯一标识 |
| action | String | 是 | `APPROVE`（通过）或 `REJECT`（驳回） |
| remark | String | 否 | 审批备注，最长 500 字符 |

- 仅待审批状态可审批；已审批（重复点击或状态过期）返回 HTTP 409 / 10005。
- 相同 `bizNo` 重试返回首次成功结果；相同 `bizNo` 不同内容返回 HTTP 409 / 17004。
- 审批只改审批状态，不立即修改维修人员工作状态；请假生效由后台任务完成。

### 13.5 后台生效与结束（不暴露接口）

- 生效任务每分钟扫描已通过、已到开始时间且未结束的请假：维修人员置为请假中，其待接单/维修中/返工中/已中断工单逐单重新派单；全部成功记 `reassignStatus=2`，存在失败记 `3` 并生成管理员汇总提醒。
- 结束任务每分钟扫描已到结束时间的请假：不存在其他生效请假时把维修人员恢复为正常；请假期间已转出的工单不会自动转回。

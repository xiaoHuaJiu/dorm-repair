# 维修人员请假接口

> **状态：开发完成，暂未测试。** 项目当前无法启动，本章契约未经运行时验证，前端接入前需先联调。

本文是 PLAN-9（维修人员请假）的接口契约，覆盖维修人员请假申请、管理员请假审批以及后台请假生效与结束。响应遵循《公共接口响应规范.md》。

## 1. 接口一览

| 接口 | 方法 | 角色 | 用途 |
|---|---|---|---|
| `/api/worker/leave-requests` | POST | 维修人员 | 幂等提交请假申请 |
| `/api/worker/leave-requests` | GET | 维修人员 | 本人请假申请分页 |
| `/api/worker/leave-requests/{id}` | GET | 维修人员 | 本人请假申请详情 |
| `/api/admin/leave-requests` | GET | 管理员 | 全量请假申请分页与组合筛选 |
| `/api/admin/leave-requests/{id}` | GET | 管理员 | 任意请假申请详情 |
| `/api/admin/leave-requests/{id}/review` | POST | 管理员 | 审批请假申请（通过/驳回），幂等 |

请假生效与结束不暴露 HTTP 接口，由后台定时任务完成（见第 6 节）。

## 2. 状态约定

### 2.1 审批状态 `approvalStatus`

对应 `repair_leave_request.status`：

| 值 | 名称 | 说明 |
|---|---|---|
| 0 | 待审批 | 创建后的初始状态 |
| 1 | 已通过 | 管理员同意，但不代表请假已经开始 |
| 2 | 已驳回 | 管理员驳回，不占用时间段 |

### 2.2 转派处理状态 `reassignStatus`

对应 `repair_leave_request.reassign_status`，仅对已通过的请假有意义：

| 值 | 名称 | 说明 |
|---|---|---|
| 0 | 未处理 | 尚未到开始时间，或已到开始时间但任务尚未处理 |
| 1 | 处理中 | 生效任务已抢占，正在逐单转派；超时未更新视为中断 |
| 2 | 已完成 | 全部工单转派成功，或无需转派 |
| 3 | 部分失败 | 存在转派失败的工单，失败工单已进入待人工派单 |

### 2.3 维修人员工作状态 `workStatus`

对应 `repair_worker.work_status`：`0 正常`、`1 请假中`、`2 停用`。请假生效后置为 `1`，请假结束且无其他生效请假时恢复 `0`。

## 3. 提交请假申请

`POST /api/worker/leave-requests`。只允许维修人员；`workerId` 由后端从登录上下文解析，前端不得指定。

### 3.1 请求

```json
{
  "bizNo": "8d4892f9-5f58-45a7-bd03-7cb8a670eb12",
  "startTime": "2026-09-25T08:00:00",
  "endTime": "2026-09-26T18:00:00",
  "reason": "家中有事需要请假两天"
}
```

| 字段 | 类型 | 必填 | 校验 |
|---|---|---|---|
| bizNo | String | 是 | 最长 64 字符；同一次重试保持不变 |
| startTime | LocalDateTime | 是 | 必须早于 endTime |
| endTime | LocalDateTime | 是 | 必须晚于当前时间 |
| reason | String | 是 | 最长 500 字符 |

### 3.2 成功响应

```json
{
  "code": 0,
  "message": "success",
  "data": { "leaveId": 10001, "approvalStatus": 0 }
}
```

### 3.3 时间重叠校验

服务端只检查与「待审批」「已通过」请假的重叠，时间区间为 `[startTime, endTime)`：

- 首尾相接（新请假 `startTime` 等于已有请假 `endTime`）不视为重叠。
- 已驳回的请假不参与重叠校验，可重新申请相同时间段。
- 存在重叠：HTTP 409 / 10005，文案「该时间段与已有待审批或已通过的请假重叠」。

### 3.4 幂等规则

- 相同维修人员、相同 `bizNo`、相同请求摘要再次提交：返回首次创建结果，不创建第二张请假单。
- 相同 `bizNo` 但请求内容不同：HTTP 409 / 17004。
- 相同 `bizNo` 的请求仍在执行：HTTP 409 / 17003，前端应提示「请假申请正在提交中，请勿重复操作」，不得自动更换 `bizNo`。

### 3.5 错误场景

| 场景 | HTTP | 业务码 |
|---|---|---|
| 参数缺失或格式错误 | 400 | 10001 |
| 开始时间不早于结束时间 | 400 | 10001 |
| 结束时间不晚于当前时间 | 400 | 10001 |
| 时间段与已有待审批/已通过请假重叠 | 409 | 10005 |
| 相同 bizNo 不同内容 | 409 | 17004 |
| 请求仍在执行 | 409 | 17003 |
| 匿名访问 | 401 | 10002 |
| 非维修人员角色 | 403 | 10003 |
| 当前账号无维修人员档案 | 404 | 15002 |

## 4. 维修人员查询

### 4.1 本人请假分页

`GET /api/worker/leave-requests`。服务端强制限定当前维修人员，前端不得传 `workerId`。

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| pageNum | Integer | 否 | 默认 1，最小 1 |
| pageSize | Integer | 否 | 默认 10，最大 100 |
| approvalStatus | Integer | 否 | 按审批状态筛选（0/1/2） |

### 4.2 本人请假详情

`GET /api/worker/leave-requests/{id}`。只能查看本人请假，非本人记录返回 HTTP 404 / 10004。

### 4.3 列表项与详情结构

列表项字段：`leaveId`、`workerId`、`workerName`、`workerNo`、`startTime`、`endTime`、`reason`、`approvalStatus`、`approvalStatusName`、`reassignStatus`、`reassignStatusName`、`reviewAdminId`、`reviewAdminName`、`reviewRemark`、`reviewTime`、`createTime`。

详情在列表项基础上增加 `updateTime`。

    "endTime": "2026-09-26T18:00:00",
    "reason": "家中有事需要请假两天",

## 5. 管理员查询与审批

### 5.1 全量请假分页

`GET /api/admin/leave-requests`。

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| pageNum | Integer | 否 | 默认 1，最小 1 |
| pageSize | Integer | 否 | 默认 10，最大 100 |
| workerId | Long | 否 | 按维修人员筛选 |
| approvalStatus | Integer | 否 | 按审批状态筛选（0/1/2） |
| startTime | LocalDateTime | 否 | 请假开始时间下限 |
| endTime | LocalDateTime | 否 | 请假开始时间上限 |

### 5.2 任意请假详情

`GET /api/admin/leave-requests/{id}`。结构同第 4.3 节。

### 5.3 审批请假

`POST /api/admin/leave-requests/{id}/review`。只允许管理员。

```json
{
  "bizNo": "9a2b3c4d-1234-5678-90ab-cdef01234567",
  "action": "APPROVE",
  "remark": "同意"
}
```

| 字段 | 类型 | 必填 | 校验 |
|---|---|---|---|
| bizNo | String | 是 | 最长 64 字符；同一次重试保持不变 |
| action | String | 是 | `APPROVE` 或 `REJECT` |
| remark | String | 否 | 最长 500 字符 |

规则：

- 仅「待审批」状态可审批；请假不存在返回 HTTP 404 / 10004；已审批返回 HTTP 409 / 10005。
- 审批只修改审批状态与审批信息（审批人、备注、时间），不修改维修人员工作状态。
- 相同 `bizNo` 相同内容重试：返回首次成功结果（幂等重放）；相同 `bizNo` 不同内容：HTTP 409 / 17004。
- 并发审批由数据库条件更新保证只有一个成功，其余返回 HTTP 409 / 10005。
- 成功响应统一为 `{"code":0,"message":"success","data":null}`。

## 6. 后台生效与结束

### 6.1 请假生效（转派）

由 `RepairLeaveEffectiveTask` 每分钟扫描「已通过 + 已到开始时间 + 未到结束时间」的请假：

1. CAS 抢占任务（`reassign_status` 0→1），防止重复执行；处理中超过 `app.leave.stale-minutes`（默认 5 分钟）未推进的视为中断，允许重新抢占。
2. 维修人员 `work_status` → 请假中，此后自动派单候选过滤将其排除。
3. 查询该人员待接单/维修中/返工中/已中断工单，逐单按 `LEAVE_REASSIGN` 来源重新派单；单工单异常隔离，不因个别失败中断后续。转派失败的工单由派单服务置为待派单并生成单工单告警。
4. 汇总：全部成功或无需转派 → `reassign_status=2`；存在失败 → `reassign_status=3` 并生成管理员汇总提醒（`source_type=4`、`failure_reason=LEAVE_REASSIGN_PARTIAL_FAILED`）。

### 6.2 请假结束（恢复）

由 `RepairLeaveEndTask` 每分钟扫描「已通过 + 已到结束时间」的请假：

- 该维修人员当前为请假中，且当前不存在其他生效请假（连续请假判断），则 `work_status` 恢复为正常。
- 恢复后人员重新进入自动派单候选池；请假期间已转出的旧工单不会自动转回。

### 6.3 配置项

| 配置 | 默认值 | 说明 |
|---|---|---|
| `app.leave.effective-delay-ms` | 60000 | 生效任务执行间隔 |
| `app.leave.effective-initial-delay-ms` | 30000 | 生效任务启动延迟 |
| `app.leave.end-delay-ms` | 60000 | 结束任务执行间隔 |
| `app.leave.end-initial-delay-ms` | 60000 | 结束任务启动延迟 |
| `app.leave.effective-batch-size` | 100 | 生效任务单批扫描上限 |
| `app.leave.end-batch-size` | 100 | 结束任务单批扫描上限 |
| `app.leave.stale-minutes` | 5 | 处理中任务超时阈值（分钟） |

对应环境变量：`LEAVE_EFFECTIVE_DELAY_MS`、`LEAVE_EFFECTIVE_INITIAL_DELAY_MS`、`LEAVE_END_DELAY_MS`、`LEAVE_END_INITIAL_DELAY_MS`、`LEAVE_EFFECTIVE_BATCH_SIZE`、`LEAVE_END_BATCH_SIZE`、`LEAVE_STALE_MINUTES`。

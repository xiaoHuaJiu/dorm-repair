# 前端页面接口依赖矩阵

本文对应 `FRONTEND-PLAN.md` 的 F0-02。状态含义：

- **已具备**：现有接口文档明确记录已实现，可进入前端联调。
- **待联调**：接口契约已有说明，但仍需用实际后端响应核对。
- **缺失/阻塞**：现有接口文档没有可供页面完成业务闭环的正式接口。

前端不得为“缺失/阻塞”接口生成演示数据；页面应展示空状态、错误状态或禁用对应操作，并保留明确提示。

## 1. 公共协议

| 能力 | 接口/协议 | 状态 | 前端约定 |
|---|---|---|---|
| 登录 | `POST /api/auth/login` | 已具备 | 成功返回 `token` 和 `user`；JWT 使用 `Authorization: Bearer`；角色值 `1学生/2维修/3管理员` 已确认 |
| 学生注册 | `POST /api/auth/register` | 已具备 | 仅提交已确认的五个字段；注册成功不自动登录 |
| 当前用户 | 未记录 | 缺失/阻塞 | 页面刷新后用本地缓存恢复界面身份，401 时统一清理；正式当前用户接口仍缺失 |
| 文件上传 | 未记录 | 缺失/阻塞 | 报修和维修图片功能阻塞，不在前端生成假 URL |
| 分页 | `pageNum`、`pageSize` | 已具备 | 后端 `PageResult` 确认集合字段为 `records`，页码从 1 开始，`pageSize` 最大 100 |
| 统一响应 | `{ code, message, data }` | 已具备 | HTTP 状态与业务码同时判断 |

分页集合字段已由后端 `PageResult` 源码确认统一为 `records`，`list` 仅保留为内部兼容别名且不参与 JSON 序列化。

## 7. 已确认的字段和枚举基线

- 工单列表字段以 `前端联调接口说明.md` 第 4 节为准，包括 ID、编号、状态、学生、故障类型、四级位置、负责人、期限和异常标记。
- 工单详情聚合对象为 `baseInfo`、`processRecords`、`materialRecords`、`reworkRecords`、`evaluation`、`flows`。
- 页面展示状态名称为：待派单、待接单、维修中、待确认、已中断、返工中、已完成、已取消。
- 状态数值已从后端 `RepairOrderStatusEnum` 源码确认：`0待派单、1待接单、2维修中、3待确认、4返工中、5已中断、6已完成、7已取消`，前端按此映射状态颜色与筛选参数。
- 流转操作类型数值已从后端 `RepairOrderOperationTypeEnum` 源码确认：`1提交报修、2系统派单、3接单、4中断维修、5恢复维修、6提交维修结果`，后续节点（转派、返工、确认、取消）待后端扩展。
- 流转记录 `flows` 目前仅有 `operatorId`、`operatorRole` 和负责人 ID，无操作人与负责人姓名：`OrderTimeline` 已提供 `operatorNameOf`/`assigneeNameOf` 映射回调，F5 详情页联调时由页面层提供姓名映射，后端补充姓名字段后可移除回调。
- 位置层级固定为单位/校区、区域、楼栋、房间，类型值依次为 1、2、3、4。

## 8. 后端并行开发阻塞清单

1. 补充当前用户、文件上传、创建报修、重复检测和取消工单接口。
2. 补充学生全校工单和维修人员全校只读工单及详情访问契约。
3. 补充维修命令、评价返工、请假、消息、审批和人工派单接口。
4. 补充区域与故障类型的删除接口（F4 已确认前端方案：无接口期间删除按钮禁用 + 提示，有子节点节点点击提示“请先删除下级节点”）。
5. 确认 `flows` 覆盖工单整个生命周期和全部异常节点，并补充操作人与负责人姓名字段。
6. 确认后续流转操作类型（转派、返工、确认、取消等）对应的 `operationType` 数值。
7. F5 补充维修人员负载（进行中工单数）查询后，替换维修人员卡片“当前剩余 N 张工单”占位“—”。
